---

## 1. Purpose and context

An informational and educational website supporting a clinical trial of a stepped-care sleep intervention. Participants can watch short videos, listen to audio-only versions, and read, print or keep a handout for each video, which carries everything the video says. They can find content by describing their problem or by searching.

The site must stay online and freely available after the grant ends, with close to zero cost and maintenance. That requirement drives most of the design decisions below.

**Site engagement is not a trial outcome.** Analytics, ratings and feedback are for improving and reporting on the resource only. They are anonymous and are never linked to participants.

## 2. Design principles (in priority order)

1. **Static first.** All content is pre-built HTML/CSS/JS. Dynamic features are optional enhancements.
2. **Graceful degradation.** If the API is down, disabled or blocked, every page still works fully as a content site. No feature may block page rendering.
3. **Low maintenance.** Minimal dependencies, no client-side framework, no server we administer, nothing that needs regular patching to stay secure.
4. **Privacy by default: no tracking, and everything disclosed.** SleepSteps sets no cookies and no persistent identifiers, stores no IP addresses, and loads no third-party scripts beyond §16.2. Any storage on a visitor's device, whether ours or a provider's (YouTube after play, Turnstile, Cloudflare security checks), is listed in §15.4 and on the privacy page.
5. **Editable by non-developers.** Content and keyword changes need only GitHub's web editor or a CSV upload.
6. **Accessible.** WCAG 2.2 AA.

## 3. Non-goals

- User accounts, logins or personalisation
- Linking any data to trial participants or study IDs
- Server-side rendering or a CMS for the public site. The staff-only admin pages (`/admin/`, behind Cloudflare Access) are the only pages the Worker renders (§14.4)
- Displaying ratings or aggregate scores publicly
- Comments or any user-generated content shown on the site
- Real-time monitoring of feedback (the site must state that feedback is not monitored for urgent issues)

## 4. Architecture overview

```
                    GitHub repo (source of truth)
                              │  push to main
                              ▼
                    Cloudflare Workers Builds
                    (npm run build → wrangler deploy)
                              │
                              ▼
 Browser ──HTTPS──▶  Cloudflare edge (DNS, bot controls, rate limiting)
                              │
               ┌──────────────┴───────────────┐
               ▼                              ▼
     Static assets (dist/)            Worker (worker/index.js)
     HTML, CSS, JS, MP3, PDF,         /api/*           → D1 database
     search-index.json                /admin, /admin/* → Access + the Worker's
                                                         token check, then D1
                                              │
                                              ▼
                                        D1 (SQLite)
                                        ratings, feedback, events

 External: YouTube (video embeds via youtube-nocookie.com)
           Cloudflare Turnstile (spam protection on feedback)
```

A single Worker serves both the static site and the API. Requests that match a static file are served directly (free, unlimited). Other requests reach the Worker code, and so does every `/api/*`, `/admin` and `/admin/*` request, whether or not a file matches (`run_worker_first`, §18.2). `worker/index.js` only builds the handler: the routing and the API's checks are in `worker/router.js` (§14.1), and the admin pages' checks in `worker/routes/admin.js` (§14.4).

## 7. Content model

The site is organised around **sleep problems** (design handoff, §22). People pick a problem; each problem page shows a video about the problem and the solution videos for it, or, for a stand-alone problem, the one video made for it (§7.2). Videos live in a shared library and can appear on more than one page.

**Placeholder content.** Until the team supplies the real content, placeholders build and are easy to find. Placeholder text is in `[square brackets]`. A placeholder video has `placeholder: true` and `youtube_id: "PLACEHOLDER"`, and its duration may be `"[mm:ss]"`: its frame shows "[Video coming soon]" with no link or button, so it never contacts YouTube; the ratings widget (§12) still shows under it, and the page still ends with the YouTube note (§9.1, §15.1), so pages read as they will at launch. The build lists placeholder videos as a warning (without also warning that they have no handout or audio, §7.1); at launch there must be none (M8). A placeholder may keep a stand-in transcript in brackets (not shown on the site, §7.1), but a real video may not (the build fails, as it does for a bracketed duration, since the search would index it). The sample content is one placeholder video per problem (`<slug>-about`), the eight placeholder mechanism videos of the solution library (§7.1) and the three intro videos. Every problem has bracketed "Is this you?" text. The 23 problems that use the mechanism videos have the solutions the team's planning sheet gives them (§7.2), with bracketed blurbs; the 13 stand-alone problems have none, and their own video's bracketed title names the video made for them. Between them they show the layouts the content has: `cant-get-back-to-sleep` (3 main, 3 extra), `tired-but-wired` (3, 2), `stress-and-worries` (3, 1), `sleep-timing-all-over-the-place` (3, 0), `putting-off-going-to-bed` (2, 2) and the stand-alone `sharing-a-bed` (no solutions); no problem in the sheet has a single main solution, so that layout (still allowed, "1 main solution") appears on no page. Four problems also have placeholder related topics: `tired-but-wired`, `cant-get-back-to-sleep`, `pain` and `hot-flushes-and-night-sweats`. Small placeholder files in `media/` (a one-page PDF and two seconds of silent MP3) let the handout and audio controls be seen: some mechanism videos carry them, as do three stand-alone videos (`sharing-a-bed-about` has every format, `sleeping-in-hospital-about` audio only and `snoring-about` a handout only), so every combination of formats the templates are tested with is on some page (`content.test.js`).

**Identifiers.** Every page has a `page_id`: a problem's slug, a fixed ID for the main pages (`home`, `start`, `problems`, `search`), or an information page's file name. Every video has a `video_id` (its file name). Both are lowercase, hyphenated and stable. **Never rename a `page_id` or `video_id` without adding a redirect (for pages) and updating every reference and `keywords.csv`.** `validate-content.js` fails the build on any dangling reference.

### 7.1 Videos (`content/videos/<video_id>.md`)

Videos have no page of their own (`permalink: false`); problem pages and Start here embed them.

```yaml
---
title: "Sleep drive"
youtube_id: "AbCdEfGhIjK"
duration: "6:40"
audio: "sleep-drive.mp3"             # file in media/audio/: the video's soundtrack (§9.2); every video, by launch
handout: "sleep-drive.pdf"           # file in media/pdf/; every video, by launch (format still open, §9.3)
thumbnail: "sleep-drive.jpg"         # optional, file in media/thumbs/
placeholder: true                    # optional: not on YouTube yet (§7)
---
Optional: the transcript in Markdown (the body). No page shows it; the site search indexes it (§8.3, §9.3).
```

Required fields: `title`, `youtube_id` (the 11-character ID, in quotes) and `duration` (`"m:ss"` or `"h:mm:ss"`, in quotes). **Every video is to have a handout and an audio-only version** (§9.2, §9.3); the handout is the video's text alternative and carries its full narration (§9.3). The page hides any format a video doesn't have, so placeholder videos, which may have none, still build. The build warns about a video that is not a placeholder and has no `handout` or no `audio`, and the launch check (`node scripts/validate-content.js --no-placeholders`, M8) fails on any video without both. **A transcript (the file's body) is optional, and no page shows it** (project lead, 2026-11-06): the site search indexes it (§8.3), and it can be the source of the YouTube captions (§9.1). Where there is one it is plain Markdown: no headings, no HTML (tags or comments; the search index drops a comment, so a comment-only body would index nothing), no images, and no links except to pages on this site (paths starting with `/`). That keeps the search text and the caption source plain, and the text safe to show if a page ever does: headings would break a page's outline, an image would load from elsewhere, and a link out would skip the §16.1 allowlist and `noreferrer`. Media fields are bare file names with the right extension (`.mp3`, `.pdf`, or `.jpg`, `.jpeg`, `.png`, `.webp`). The build fails if a referenced media file does not exist, if audio is over 25 MiB (§9.2), or on an unknown field (usually a typo). It warns about a video used on no page.

Templates read a video through the `videoById` filter (`eleventy.config.js` documents the shape it returns: the front matter, without the body). No page shows a video's body, so no page needs `eleventyImport` for the videos.

**The library.** There are three kinds of video:

- **Problem videos**, one per problem (`<slug>-about`, its `problem_video`): about that problem, or, for a stand-alone problem (§7.2), the one video made for it.
- **The solution library: eight mechanism videos**, each on one process that keeps sleep problems going, shared by the problems that list them as solutions (§7.2). Their ids and titles come from the team's script names: `sleep-drive` (Sleep drive), `circadian-rhythm` (Circadian rhythm), `conditioning` (Conditioning), `cognitive-arousal` (Cognitive arousal; on sleep-related thoughts, beliefs and attention), `physiological-arousal` (Physiological arousal), `sleep-effort-and-control` (Sleep effort and control), `treatment-symptoms-and-sleep` (Treatment, symptoms and sleep; the cancer-specific one, including pain) and `daytime-rhythms-and-sleep` (Daytime rhythms and sleep). Until the videos are made they are placeholders with bracketed titles and stand-in transcripts; the draft scripts are not copied into the repo.
- **Intro videos**, the Start here chapters (§7.3).

### 7.2 Areas and problems

**Areas (`data/areas.csv`).** The 10 groups problems are shown in. Edited in Excel like `keywords.csv`.

```csv
area_id,name,description,source_name,order
core,Falling and staying asleep,"Trouble getting to sleep, staying asleep, or waking unrefreshed.",Core insomnia problems,10
```

**Problems (`content/problems/<slug>.md`).** One file per problem, rendered at `/problems/<slug>/`.

```yaml
---
title: "Tired but wired"                       # short title: menus and H1
statement: "I'm tired, but I can't fall asleep" # the first-person line
source_title: "I am struggling to fall asleep at night: 1) ..."  # the team's original wording, not shown
area: core                                      # area_id from areas.csv
time_of_day: bedtime                            # evening | bedtime | night | early-morning | day | any
order: 10                                       # order within the area
new: false                                      # shows a "New" pill
problem_video: tired-but-wired-about            # video_id
standalone: false                               # optional; true: one video made for this problem, and no solutions
is_this_you:
  summary: "One or two plain sentences."
  bullets: ["...", "..."]                       # 2–4 items
solutions:                                      # 1–3 main, 0–3 extra, in display order; none if standalone
  - { tier: main, video: conditioning, blurb: "Try this if ..." }
  - { tier: extra, video: sleep-effort-and-control, blurb: "Try this if ..." }
related: [not-sleepy-at-bedtime, stress-and-worries]   # 2–3 hand-picked problem slugs
---
```

**Solutions follow the team's planning sheet** ("Latest videos by problems"). For each problem it marks each of the eight mechanism videos (§7.1) `1` (a main solution), `2` (an extra) or not used, and names a suggested start. The main solutions list the suggested start first, then the sheet's other 1s in its column order (sleep drive, circadian timing, conditioning, cognitive arousal, physiological arousal, sleep effort, treatment and symptoms, daytime rhythms); the extras follow, in the same order. The sheet gives each problem 2–3 main and 0–3 extra solutions. A problem's `source_title` is the team's module wording from the sheet, so a row can be matched to its file by meaning; six still carry earlier wording, so don't expect an exact text match.

**Stand-alone problems** (`standalone: true`) are the sheet's "Separate video" rows: one video made for that specific problem, rather than the mechanism videos. That video is the problem's `problem_video`, whose title names it, and the problem has no `solutions`. There are 13: `uncomfortable-sleep-environment`, `sleeping-in-hospital`, `sharing-a-bed`, `parents-of-young-children`, `involving-others`, `sleep-not-improving-yet`, `setbacks-and-bad-nights`, `following-sleep-advice`, `if-sleep-problems-return`, `dreams-and-nightmares`, `snoring`, `restless-legs` and `accepting-changes-to-my-sleep`. Their page leaves out the solutions (§7.5).

The build fails on an unknown `area`, `time_of_day`, `video` or `related` slug, or on solution counts outside 1–3 main / 0–3 extra. A problem either has `standalone: true` and no solutions (no `solutions`, or an empty list) or 1–3 main and 0–3 extra: a stand-alone problem with any solution fails, as does any other problem with none, and each message names the other way out; a `standalone` that isn't true or false fails too. It also fails on a missing `title`, `statement`, `order` or `problem_video`, a solution without a `blurb`, the same video twice on one page (the problem video and its solutions: their ids and ratings would clash), a problem listed in its own `related`, more than 3 `related` or more than 4 bullets. It warns, without failing, when `related` has fewer than 2 entries, `is_this_you` is empty or has fewer than 2 bullets, or a field isn't one the templates read, so placeholder content can still build.

The **Sleep problems** page (`/problems/`) lists every problem in two views, chosen with a two-way slider: "By area" (the default) and "When it happens". Both views are the same accordion, built by one template macro: one group per area (`data/areas.csv`) or per time of day, each a heading with the group's name, its number of topics and, for areas, the description, over the same topic cards. The times of day are `time_groups` in `content/problems.njk` (`id` and `name`, in display order: In the evening, At bedtime, During the night, Early morning, During the day, Any time); their ids are the `time_of_day` values, and the build fails on a problem whose `time_of_day` has no group. Problems keep the collection order (area, then `order`) within a time of day. Area anchors such as `/problems/#core` open that area in the By area view; times of day have no anchors, since `day` is both an area and a time of day. Without JavaScript, every area renders open under a plain heading, and the filter, the view toggle and the "When it happens" view are not shown (they need JavaScript; the areas already list every problem), nor is the band's sentence about them. `src/js/problems.js` turns each group heading, in both views, into a `<button aria-expanded aria-controls>`, starts every group of both views closed (project lead, 2026-11-07), except the area named in the URL, which it opens, and shows the toolbar. There is no "Open all areas" button.

### 7.3 Start here (`content/start.md`)

Lists the intro videos in order, in `chapters`: each has a `video` (video_id) and a one-line `description`. The title, duration and formats come from the video file. Rendered at `/start/`, with chapters `#v1`, `#v2`, ... The build fails on an empty list, an unknown or repeated video, a missing description or an unknown field.

### 7.4 Information pages (`content/pages/*.md`)

Standard Eleventy pages with `title` and `summary`. They are included in the search index unless `search: false` is set. A page's `page_id` is its file name and it renders at `/<file name>/` (`content/pages/pages.11tydata.js`).

They use the information layout (`src/_includes/layouts/info.njk`, whose header comment is the full contract): a teal title band, then the content in one column, with no side menu (§7.5, §22). The header links to Get more help, Contact and Getting urgent help, and the footer to all five information pages (About and Privacy and your data only there; project lead, 2026-11-07). Front matter: `title` and `summary` (required; the summary is the lede under the H1 and the meta description), and optionally `eyebrow` (default "Information"), `heading` (H1 text when it differs from the title), `band: hero` (the About hero with the settling arc) and `styles` (extra stylesheets, e.g. `["pages/help.css"]`). Any page can list `styles`; only paths under `src/css/` are accepted. Likewise `scripts` (e.g. `["players.js"]`) loads extra ES modules from `src/js/` (file names only). A page never lists `events.js` or `feedback.js`: `base.njk` adds them where they are needed, and the build fails if a page lists either (§10.1, §13). A layout can list `styles` and `scripts` in its own front matter too (`layouts/problem.njk` does); Eleventy merges them with the page's. `track_page_view: true` marks the pages that send a `page_view` (§10.2): problem pages, Start here and Getting urgent help. `base.njk` renders it as `<body data-page-view>` whatever the feature switches say, and both `events.js` and `pages.json` (§8.3) read that marker.

Required pages: Get more help (`/help/`, whose "Other support" cards start with Cancer Council: 13 11 20 and a link to its website, §16.1), About us (`/about/`; the footer's link keeps "About", §7.5), Contact (`/contact/`, with the project email, psych.sleepsteps@monash.edu), Privacy and your data (`/privacy/`, §15), Getting urgent help (`/urgent-help/`, with the crisis contacts from `site.config.json`), and 404 (`content/404.njk`, output as `/404.html`, no `page_id`).

**Getting urgent help is deliberately minimal** (design handoff §6.5): it uses `layouts/urgent.njk`, which sets `header: minimal` (the logo and "Back to home" only: no nav, search box or menu script). It has the site footer, as every page does (project lead, 2026-11-07), so "Send feedback" is here too (§13); it is the one exception to the header search box (§8.1). Under the crisis cards (§11), smaller white cards come from the page's `other_contacts` front matter (`heading`, `description`, optional `value`, and an optional website in `url` with its `link_text`): a card whose `value` is a confirmed number (not a `[placeholder]`) is a whole-card `tel:` link with the hover shadow, unless it also has a website, when only the number is a `tel:` link, since one link can't hold another. "Your treating team" has no number (it is on each person's care plan), so its card is information, not a link. The cancer support line is Cancer Council, 13 11 20 (Australia): a free, confidential information and support line, open 9am to 5pm, Monday to Friday (longer in some states), and not a crisis service. Its card gives the number as a `tel:` link, the hours and a link to its website, `https://www.cancer.org.au/` (§16.1). Get more help's `services` cards take the same optional `url` and `link_text`. The page carries no draft or developer notes (a test checks this); what the team still has to confirm is tracked in §21.

### 7.5 Visual design and components

Layouts, copy and components follow the design handoff in `docs/design/` (start with `HANDOFF.md`; the boards in `reference/boards/` give exact spacing and copy, but their design-tool runtime is not copied). Its colour, type-scale, spacing and radius tokens are CSS custom properties defined once in `src/css/tokens.css`, the only stylesheet allowed to contain colour values (a test enforces this); components never hard-code values. `src/css/site.css` holds the base styles, the shell components and the page layouts; `src/css/components.css` holds the components shared by several pages (the video facade, the row of controls under each video with its format buttons and ratings widget, step chips, buttons, section headings and topic cards); a page adds its own CSS through `styles` front matter (§7.4).

Token rules:

- **Spacing:** the token scale (4–32px) plus layout steps `space-9` to `space-14` (40, 48, 56, 64, 72, 96px) for page padding and section gaps. Board values off the scale snap up to the next step (10→12, 14→16, 18→20, 22→24, 28→32, 36→40, 44→48).
- **Type:** the tokens.json styles, plus values the handoff gives outside it: interior H1 48px, problem H1 44px, phone H1 34px (Home's display line too, where Landing-Phone has 38px), the 19/30 lede and the problem statement at 22px. All running text is at least 17px; the boards' 15–16px running text is raised to 17px. Other off-scale headings snap to the nearest token style: the phone boards' 26px section headings use the 24px title size.
- **Colour pairs:** only pairs tokens.json lists as passing. So the footer's secondary text is `paper` (the board's `on-teal-muted` on `ink` is not listed), the urgent-help notice text is `clay-deep` on `clay-wash`, and links on a `panel` ground (the Sleep problems nudge) are `ink`.
- **Focus ring:** 2px solid with a 2px offset, `deep-teal` on light grounds and `paper` on teal or ink (handoff §10), with two exceptions. On the urgent-help notice's `clay-wash` ground the ring is `clay-deep`, the only colour tokens.json lists on that ground. The header search input is joined to its `deep-teal` submit button, so its ring is drawn just inside the input's box (at the usual offset its right side would sit on the button and vanish).

## 8. Search

### 8.1 Behaviour

- A search box in the header on every page except Getting urgent help (§7.4). Submitting goes to `/search/?q=<query>` (a plain GET form, so it works without JavaScript). The search page has its own form too (the header's is in the phone Menu), labelled "Search this website" (§7.5).
- The search page loads `search-index.json` and MiniSearch lazily, i.e. only on the search page or when the header box is focused: `src/js/search.js` loads them on `/search/` (their addresses are `data-` attributes on the page), and the first focus on a header search box adds `<link rel="prefetch">` for the same two files (`menu.js`), so the results page finds them in the browser's cache. If either fails to load within 15 seconds, the page says "Search isn't working right now." and links to the Sleep problems page.
- Results show title (linked, an H2), content type ("Sleep problem", "Introduction" or "Information") and summary, built with `textContent` only. Show the top 10. The count goes in a `role="status"` line ("3 results for “night sweats”", or "The top 10 of 24 results for …").
- With no results, show a message plus a link to the Sleep problems page.
- Under the form, on every search and also without JavaScript: "If you feel unsafe or need help right now, go to Getting urgent help." (the urgent notice style). Someone in distress may type it into the search box, and ranking alone doesn't always put Getting urgent help first for every way of saying it ("I can't go on", "not coping"); crisis words such as "suicidal" do (§8.4).
- The query is kept in the URL so results are shareable and the Back button works.
- Log a `search` event with the query (trimmed and cut to 100 UTF-16 code units) and the number of results (§10.2). `search.js` dispatches it as a `sleepsteps:event` DOM event, as `players.js` does, and `events.js` sends it without the visit code (§10.1). A search that fails to load sends nothing. The query is never logged to the console or kept in browser storage, and it is stored only as that event (§10.1, §15.3).
- **The query never travels on in a referrer.** The search page sets `<meta name="referrer" content="strict-origin">` (front matter `referrer`, read by `base.njk`), so a page reached from it (a result, the nav) sees only the site's address in `document.referrer`. Otherwise the full `/search/?q=…` address would be the next page's referrer, and YouTube's player script copies `document.referrer` into the embed when someone presses play there (§9.1). The site-wide `strict-origin-when-cross-origin` (§16.1) still sends the full address to same-origin pages, so it isn't enough here. The same policy keeps the query out of the `Referer` header of the search event's own request (§10.1): browsers add that header to beacons, and it would otherwise carry the whole `/search/?q=…` address, uncut. A referrer policy governs only that header, not what a script running in the page reads: the search page has the feedback dialog too, and opening it loads Turnstile, whose script sends Cloudflare the page's full address, query included (decision A4, §13, §15.2, §21).
- With JavaScript disabled, the search box still submits to `/search/`, whose static HTML says that results need JavaScript and links to the Sleep problems page.
- **Problems page filter** (separate from the site search, and labelled differently, §7.5): a live filter on `/problems/` matching each problem's short title, statement, area name and keywords. Words in the query must all match; commas or semicolons separate alternatives ("night sweats, 3am"). It filters both views as you type, so switching view keeps the filter. While some topics match, it hides groups (areas, or times of day) with no matches and opens groups with matches, and it announces the count ("4 topics match “night”") in an `aria-live="polite"` region once typing pauses. When nothing matches, or the field is cleared, both views go back to how they were before the filter narrowed them: every group shows (one with no topics included, as on load), opened or closed as before, and when nothing matches the result line says so. It does not log events, and the query is never stored, sent or put in the URL. It needs JavaScript and is not shown without it (§7.2).

### 8.3 Index build (`scripts/build-data.js`)

Every Eleventy build (so `npm run build`, `npm run dev` and the tests' build) writes `dist/search-index.json`: `content/search-index.11ty.js` passes the collections to `searchIndex()` in `scripts/build-data.js`. The file is an array of:

```json
{ "id": "hot-flushes-and-night-sweats", "url": "/problems/hot-flushes-and-night-sweats/", "title": "...",
  "summary": "...", "keywords": "hot flushes hot flashes ...", "transcript": "plain text", "type": "problem" }
```

There is one entry per searchable page: every problem (`type` `problem`), Start here (`start`), and every information page in `content/pages/` (`page`) unless its front matter has `search: false`. Home, the Sleep problems page and the search page are not entries. A problem's `summary` is its statement, and its `transcript` field joins its "Is this you?" summary and bullets with the titles, blurbs and transcripts of every video on the page (a video's transcript is its file's optional body, which no page shows, §7.1, §9.3), so a match in a solution video's transcript leads to the problem page. Start here's joins its intro videos' titles, descriptions and transcripts. An information page's is the text of its rendered body (taken from `collections.all`, which holds every page whatever order Eleventy renders them in; a config-API collection could be computed before a page that imports a collection has joined it). Transcript Markdown and page HTML are reduced to plain text.

**`worker/generated/pages.json`** is what the Worker checks events, ratings and feedback against, and where a feedback message's stored `page_title` comes from (§12, §13, §14.1, §14.2):

```json
{ "pain": { "url": "/problems/pain/", "title": "Pain", "page_view": true, "videos": ["pain-about", "settling-your-body"] } }
```

- **Built by every full Eleventy build** (`npm run build`, `npm run dev` and `npm run dev:collect`, and the tests' build): an `eleventy.after` hook in `eleventy.config.js` passes the rendered pages to `pagesIndex()` in `scripts/build-data.js` and writes the result with `writeIfChanged()`. It always writes the repository's own `worker/generated/pages.json`, whatever the output directory, so the tests' build in a temporary directory leaves it ready for the Worker tests and `wrangler deploy`. The watch rebuilds of `npm run dev` are full builds and rewrite it. An incremental rebuild (Eleventy's `--incremental`, which no script uses) renders only some pages, and a dry run renders none, so both leave the file as it is. It is git-ignored (§6), so run `npm run build` before `wrangler dev` or `wrangler deploy` (`npm run dev` and Workers Builds do).
- **Read from the rendered HTML**, so the Worker accepts exactly what the browser modules can send. Every page whose `<body>` has a `data-page-id` is an entry: every page except the 404 page (the problems, `home`, `start`, `problems`, `search` and the information pages). `title` is the `<title>` text. `page_view` is whether `<body>` has `data-page-view` (`track_page_view`, §7.4), and it doesn't depend on the feature switches. `videos` lists every `video_id` the page names in `data-video` (the facade), `data-handout` (the handout links), `data-media` (the audio player) or `data-rating` (the ratings widget, §12), sorted and without repeats (§9.4).
- **The build fails** on a `page_id` or `video_id` that isn't lowercase words joined by hyphens, on a `page_id` used by two pages, and when no page has a `page_id`.
- Keys are sorted, and the file is rewritten only when its text changes, through a temporary file and a rename, so `wrangler dev` never reads half a file.

### 8.4 MiniSearch configuration (starting point; tune against real queries)

```js
// src/js/search-config.js, shared by search.js and the query tests
new MiniSearch({
  fields: ['title', 'keywords', 'summary', 'transcript'],
  storeFields: ['title', 'url', 'summary', 'type'],
  processTerm: (t) => t.toLowerCase().normalize('NFD').replace(/[\u0300-\u036f]/g, '')
});
// search options
{ boost: { keywords: 4, title: 3, summary: 2, transcript: 1 },
  fuzzy: 0.2, prefix: true, combineWith: 'OR' }
```

`test/node/search-queries.test.js` runs real example queries against the built index with these settings and checks their expected top results, e.g. `"hot flashes"` → `hot-flushes-and-night-sweats` in the top 3. It also checks a list of crisis words (suicide, suicidal, self harm, hurt myself, crisis, emergency, unsafe, lifeline, 000, 13 11 14): each must rank `urgent-help` first. Keyword or setting changes must keep both passing. It runs with `npm test`, so it reruns after every keyword change.

## 9. Media

### 9.1 Video (YouTube)

- Use a click-to-load facade: a 16:9 frame (the video's self-hosted thumbnail if it has one, otherwise a plain `night-teal` frame), the video title, a duration badge and a play button. The title is a visible plate on the frame where no nearby heading names the video (a problem's own video); elsewhere it is the play control's accessible name. Load the YouTube player only after the user clicks, so YouTube isn't contacted until someone chooses to play. Never autoplay before that click.
- Then create the player via the IFrame Player API with `host: 'https://www.youtube-nocookie.com'` and `playerVars: { rel: 0, playsinline: 1, autoplay: 1, cc_load_policy: 1, cc_lang_pref: 'en' }`. The player exists only after the click, so `autoplay` starts the video the visitor chose. The iframe's `title` names the video, and focus moves to it, unless the visitor has moved focus elsewhere while the player loaded. No `hl` (the player follows the viewer's language) and no `origin` (the API adds it). The `host` option works (the API builds the iframe from it) but isn't in the IFrame API reference (checked 2026-11-06).
- **Captions are on by default** (§21). `cc_load_policy: 1` shows them when the player loads, even if the viewer has turned captions off on YouTube; they can still turn them off in the player (the CC button or the c key). `cc_lang_pref: 'en'` asks for the English track. The team uploads each video's captions as a plain "English" track, not a regional one such as "English (Australia)" that `en` may not match, made from the script or transcript (Studio's Auto-sync, or a timed `.vtt`/`.srt`), and a person checks them before the video goes public (§19.2). Don't rely on auto-captions: YouTube doesn't document whether `cc_load_policy` shows an auto-generated track when there is no uploaded one (third-party reports say it often doesn't), and their accuracy varies.
- A link to watch on YouTube is shown as a fallback: without JavaScript the facade is that link, and if the player can't load (the API script fails or takes over 15 seconds, or the player reports an error) the frame says "The video couldn't load here." with the link. The link has no caption parameter: the watch page has no documented one, so there the viewer's own caption setting applies.
- YouTube blocks embedded playback when the request has no `Referer` ("error 153"), so the `Referrer-Policy` in §16.1 must never be tightened to `no-referrer`.
- A placeholder video (§7) shows "[Video coming soon]" instead of a play button, with no link.
- Ratings and formats sit outside the player.
- **The YouTube note, once per page** (project lead, 2026-11-07; it was under each facade): every page with a video ends its content with the note (§15.1), naming YouTube/Google and what may happen, with a link to the privacy page, in smaller slate-grey italic text (`notices/video.njk`'s `youtubeNote()`, from `layouts/problem.njk` and `layouts/start.njk`). Every play control names the note's sentences (`youtube-note-text`) in `aria-describedby`, so screen readers still hear it with "Play video" before pressing play, although it is at the end of the page; sighted visitors see it only if they read that far. A build test checks that each page with a video has the note exactly once, after its last video, and that every play control names it. Loading the IFrame Player API sets YouTube cookies on `.youtube.com` once someone presses play, even with the youtube-nocookie host (observed November 2026). This is disclosed (§15.4) and in the note. No YouTube request happens before the click. The note doesn't link a handout: the row of controls under each video has the video's "Handout" (§7.5, §9.3).

### 9.2 Audio

- **Every video has an audio-only version: the video's own soundtrack**, exported from the final video file as an MP3 (§21). The "Audio only" option is hidden when a video has none (placeholders); the build warns about a real video without one, and the launch check fails (§7.1).
- `<audio controls preload="none">` with an MP3 in `media/audio/`.
- **Encoding** (the commands are in `README.md`, "Exporting the audio-only version"): mono (a stereo master is downmixed), 44.1 kHz, 96 kbps constant bitrate. Loudness is normalised in two passes with ffmpeg's `loudnorm` as one linear gain, to an integrated −16 LUFS with `dual_mono` (a mono file at about −19 LUFS sounds as loud as −16 LUFS stereo, Apple's and Google's podcast targets). `loudnorm`'s true-peak ceiling is −1.5 dBTP, which leaves room for the MP3 encoder's overshoot so the finished file measures at or below −1 dBTP (Apple's podcast limit); a file that still measures higher is exported again with a −2 dBTP ceiling. The source file's metadata is removed, and ID3v2.3 tags give the title, "SleepSteps Trial Research Team" as artist (no album tag), the year, the language (`eng`) and the CC BY 4.0 notice. 96 kbps rather than 64 because the soundtrack may carry music, which 64 kbps handles less well; it costs about 1.2 MB more per 5 minutes (about 3.6 MB per 5-minute file).
- Each file must be ≤ 25 MiB (the static asset limit). At 96 kbps that is about 36 minutes per file. `validate-content.js` enforces the size limit.
- Because the audio is the video's soundtrack, the narration must say everything that matters on screen (on-screen text, numbers and demonstrations; no "as you can see"), so the audio stands on its own. That also gives the video its audio description (WCAG 2.2 SC 1.2.5, integrated description). The handout, which carries the full narration, is the audio's text alternative (SC 1.2.1, Level A; §9.3).
- Workers static assets ignore `Range` requests and send the whole file with a 200 (Cloudflare documented this in November 2026). One report says Safari still plays and seeks MP3s served that way. Check play and seek in Safari on an iPhone and in Chrome once real audio is on a preview (M8). Only if that fails, add a Worker route for `/media/audio/*` that answers with 206 (a §9.2 and §18.2 change; each play then costs Worker requests).

### 9.3 Handout, the text alternative (no transcripts on the site)

- **Every video has a handout.** Its format is still open (§21): PDF, Word or a web page. Until it is decided, `handout` names a PDF in `media/pdf/` and the page links to it as "Handout", with the video's title and "(PDF)" for screen readers (§7.5). The team supplies handouts; they are not generated. What each format would change:
  - **PDF** (today): no site work. Accessible only if exported from Word as a tagged PDF ("Best for electronic distribution and accessibility" on a Mac, document structure tags on Windows; never "Print to PDF"), checked with PAC or axesCheck, and cleaned with Word's Document Inspector. Prints as fixed A4 pages; poor on phones (no reflow) and the hardest to adapt under CC BY.
  - **Word (`.docx`)**: the easiest to adapt. The validator would accept `.docx` and the folder and labels would become format-neutral. Layout shifts with fonts and paper size, many Android phones need an app to open it, and there are no W3C techniques for checking it; Document Inspector before publishing.
  - **Web page**: the most accessible and the best on phones; readers can still print it or save it as PDF. The most site work: a `content/handouts/<video_id>.md` collection with its own URLs, print CSS for A4, a "Print handout" button (git history keeps the removed "Print transcript" code, which did the same for a transcript), validator rules and tests. The team would supply text (Word is fine) rather than finished files.
- Clicking a handout link logs `handout_open` with the video's `video_id` (§9.4, §10.2), so neither the event nor its detail depends on the format: a web-page handout would have no file name.
- **The handout is each video's text alternative** (project lead, 2026-11-06: "the handout will basically be the transcript"). With no separate transcript on the site, the handout must carry the video's full narration, word for word, naming the speakers, and anything that matters on screen, in an accessible format: it is the text alternative for the audio-only version (WCAG 2.2 SC 1.2.1, Level A), and the "Handout" in the row of controls under each video links to it (§7.5). A summary or tip sheet alone would not meet SC 1.2.1. This raises the stakes of the open format decision (§21): a PDF must be a tagged PDF, exported and checked as above, and a web page would be the most accessible. Captions are made from the script or the narration (§9.1).
- **No transcripts on the site** (project lead, 2026-11-06). No page has a "Read transcript" disclosure, a "Print transcript" button or a quick "Transcript" link, and there is no `transcript_open` event (§10.2). A video file's body may still hold a transcript (optional, §7.1): no page shows it, but the site search indexes it (§8.3), and it can be the source of the captions.

### 9.4 Media tracking (`src/js/players.js`)

- Log **one `video_play` / `audio_play` event per media item per page load**, carrying the furthest point reached: `0` (played, but under 25%), `25`, `50`, `75` or `100`. It is based on the furthest position reached, not on watch time. There are no separate progress events.
  - Send it immediately on reaching 100%. Otherwise send it when the page is hidden (`visibilitychange` to hidden, or `pagehide`) if the item was played at all.
  - If the page is hidden and shown again and the item later reaches a higher point, send one more event with the new value. Analysis takes the highest value per session, page and item.
  - A play is lost if the tab is killed without being hidden first, which is rare.
- Video: poll `getCurrentTime()` / `getDuration()` every 5 seconds while the state is PLAYING. Audio: use the `timeupdate` event.
- Log `handout_open` when a handout link (marked `data-handout`, holding the video's `video_id`) is clicked, whether the browser opens or downloads it.
- **`media` is always the `video_id`**, for every media event: the facade's `data-video`, the audio player's `data-media` and the handout links' `data-handout` (the row's "Handout" and a closed card's quick link) all hold it. So plays of two videos that share an audio file (several placeholders share `placeholder-audio.mp3`) stay apart, and the Worker checks every media event against the same list of the page's videos (§8.3).
- `players.js` sends nothing itself and uses no storage: it dispatches a `sleepsteps:event` DOM event on `document` (`{ type, detail }` in the §10.2 shapes), and `events.js`, which loads before it whenever `features.events` is on, sends it (§10.1).

## 10. Analytics events

### 10.1 Client (`src/js/events.js`)

- **Where it loads.** `base.njk`'s `moduleScripts` filter (`eleventy.config.js`) adds `/js/events.js` when `features.events` is on and the page sends a page view (`track_page_view`) or loads `players.js` or `search.js`, the modules that report events. That is the 36 problem pages, Start here, Getting urgent help and Search. It comes before every other page module (after `menu.js`, where there is one), so it is listening before they report anything. A page may not list it in `scripts` (the build fails). Production loads it before the privacy go-ahead too (§11). If `features.events` is off, it isn't loaded and the privacy page shows no switch.
- **What it sends.** On load, a page whose `<body>` has `data-page-view` sends one `page_view`; a page restored from the back/forward cache sends none. `players.js` and `search.js` report through a `sleepsteps:event` DOM event on `document` (`{ type, detail }`), and `events.js` sends each report at once, as its own request, with only the §10.2 keys of that type's detail. There is no batching and no timer, so the reports `players.js` makes as the page is hidden still get out. An unknown type, a detail missing one of its keys, or a page without `data-page-id` (where `page` comes from) sends nothing.
- **The visit code.** `session_id` is a random version 4 UUID, from `crypto.randomUUID()`, or built from `crypto.getRandomValues()` where that is missing (insecure contexts and older Safari). It is stored in `sessionStorage` as `sleepsteps-visit`, and created the first time the tab sends an event other than a search. In practice that is on load of a problem page, Start here or Getting urgent help, so Home, Sleep problems, Search and the information pages never create it. The stored code is used whenever storage can be read, and a stored value that isn't a v4 UUID is replaced. If storage throws (blocked or full), an in-memory code is used for the rest of that page. Every storage access is in try/catch.
- **Usage statistics can be turned off** on the privacy page (`src/js/stats-switch.js`, with `src/js/usage-prefs.js`, which `events.js` shares):
  - **The switch** is one button whose label says what it will do ("Turn off usage statistics" or "Turn on usage statistics"), and a status line: "Usage statistics are on in this browser." or "… off in this browser.". The line becomes `role="status"` once the script runs, so changes are announced but the first state isn't. Focus stays on the button, which has no `aria-pressed`. The switch follows a change made in another tab and a back/forward-cache restore.
  - **Turning statistics off** deletes `sleepsteps-visit`, sets `sleepsteps-stats-off` in `localStorage` (to `1`; any value counts as off) and reads it back to check it was saved. Turning them on removes the key. `events.js` reads the key before every send: while it is set, nothing is sent and the tab's visit code is deleted, so a tab that was already open stops at its next event. Ratings and feedback are unaffected.
  - **When it can't work:** if `localStorage` can't be read, the button stays hidden and the line says the browser isn't letting the site save anything, so statistics stay on; if a choice can't be saved, the line says so. Without JavaScript the line reads "Turning usage statistics off here needs JavaScript. Without JavaScript, your browser sends us no usage statistics." and the button stays hidden.
  - **While `features.events` is off**, the page shows no switch and says "This website isn't collecting usage statistics at the moment, so there is nothing to turn off."
  - All of this wording is a draft until the privacy officer approves it (§15, M8).
- **Search events carry no `session_id`**: the key is left out (the Worker refuses one, even `null`). The Worker stores them in `events` with `session_id` NULL and `ts` rounded down to the hour (§14.1). So search text is stored without the visit code and with the time rounded to the hour, which makes it hard, but not impossible, to link to the rest of a visit: `events.id` is sequential, so a search's row id falls among the ids of its visit's other rows. Exports and the admin page therefore leave out `events.id` (§14.4).
- **Sending.** `navigator.sendBeacon('/api/event', JSON.stringify(payload))`, which browsers send as `text/plain;charset=UTF-8`. If `sendBeacon` is missing, returns false or throws, it uses `fetch('/api/event', { method: 'POST', body, keepalive: true })` with no headers set (so also `text/plain`) and credentials left at their default (previews behind Access need their cookie). Nothing reads the response. There are no console calls, and every failure is silent (§11). `api.js`, the widgets' fetch wrapper (§11), isn't used.
- **Never send** a user agent, screen size, referrer, the page address's query, a timestamp (the Worker sets it) or anything typed except search queries. `events.js` never reads `navigator.userAgent`, `screen`, `document.referrer` or `location.search`. The browser adds `User-Agent` and `Referer` headers to every request itself; the Worker never reads them (§14.1), and the search page's `strict-origin` policy keeps the query out of `Referer` (§8.1).

### 10.2 Event types (closed list; the Worker rejects anything else)

| type | page | detail (JSON) |
|---|---|---|
| `page_view` | page_id: **only** problem pages, `start` and `urgent-help` (a template sets `track_page_view: true`, so their `pages.json` entry has `page_view: true`; no other page sends one) | `{}` |
| `search` | `search` | `{ "q": string, "results": int }`: `q` a string that isn't blank once trimmed, at most 100 UTF-16 code units (`search.js` cuts it there); `results` an integer from 0 to 1000. Sent **without** `session_id` (§10.1). Stored trimmed, with any lone surrogate (an emoji cut in half) replaced |
| `video_play` | page_id | `{ "media": video_id, "furthest": 0\|25\|50\|75\|100 }` (§9.4) |
| `audio_play` | page_id | `{ "media": video_id, "furthest": 0\|25\|50\|75\|100 }`: the video whose audio-only version played, not the file name (§9.4) |
| `handout_open` | page_id | `{ "media": video_id }`: which video's handout, whatever its format (§9.3) |

The body is `{ type, page, session_id, detail }` and nothing else: the Worker refuses any other key, at the top level (a client `ts` included) or in `detail`, and any missing key. "Without `session_id`" means the key is absent. Every type but `search` needs a `session_id` that is a lowercase v4 UUID. `page` must be in `pages.json` (§8.3), and `media` must be one of that page's videos. `furthest` must be one of the five numbers (the string `"25"` is refused). The Worker stores a detail rebuilt from the checked values, never the client's own text (§14.2).

- **Build time:** templates render a widget only if its feature is on. Its JS is loaded only if needed. A feature is on only when its value is exactly `true`: the templates test `=== true`, as the `moduleScripts` filter and the Worker do, and a test requires every `features` value to be a boolean (a string such as `"false"` would otherwise render widgets whose every request gets 404). `rating.js` loads only on the problem pages and Start here (37 pages), and only while `features.ratings` is on.
- **Widgets that need JavaScript ship `hidden`**, and their script reveals them once it is listening (the rating widget, §12; the feedback dialog, §13), as `problems.js` does the Sleep problems toolbar (§7.2). Without JavaScript, or if the script fails, the page is laid out as with the feature off, with one exception: while `features.feedback` is exactly `true`, the footer's "Send feedback" stays, as a link to the Contact page (§13, §22). The reveal on load is accepted; the rule below is about waiting for the API.
  - **So does text that points to them.** Home's ratings note ("Rate each video to help us improve", §7.5), which Home renders only while `features.ratings` is exactly `true`, ships `hidden data-js-only`. Home doesn't load `rating.js`, so `menu.js`, which every page with the site header loads, shows every `[data-js-only]` element. It reads no switch: the template's `=== true` test decides whether the note is there at all. Getting urgent help's minimal header doesn't load `menu.js`, so nothing there may use `data-js-only`; a test checks that every built page with it loads `menu.js` and ships each one `hidden`.
- **The one page that needs JavaScript: the admin download page** (decision B5, project lead, 2026-11-07). It is staff-only and behind Cloudflare Access (§14.4), never part of the public site. An export that fits in one request downloads from a plain link with no script, and the summary page has no script at all. A larger export opens a "download in parts" page whose script (`admin-export.js`) fetches the parts and saves one file; without JavaScript that page says plainly that the download needs it, and doesn't promise that a shorter range will work (a single day can hold more rows than one request sends). Every other page keeps working without JavaScript.
- **Worker:** imports the same file. A disabled feature's route returns `404`. Turning features off is therefore one config edit plus a push. The admin pages don't depend on `features` or `DATA_COLLECTION` (§14.4).
- **Environment:** the API also stores nothing unless the environment allows data collection: the Worker var `DATA_COLLECTION` in `wrangler.jsonc` must be exactly `"on"`; missing or any other value means off. While it is off, every `/api/*` route returns `404`, as for a disabled feature (a Worker test guards this and must be kept while the API exists). It is `"off"` in production until the privacy officer's go-ahead (§18.3), and `"off"` in previews until they are behind Cloudflare Access (§21): preview URLs are public, Workers Builds posts them on pull requests in this public repo, and preview writes count against the account's D1 limits that production shares (§17). The build has no reliable way to know whether it is building production or a preview: Workers Builds documents only the branch name (`WORKERS_CI_BRANCH`), and its API keeps separate production and preview build variables (whether the dashboard does is unverified). The API also answers only on the hosts in `API_HOSTS`, which matches no host in production until launch (§14.1, §18.2).
- **Before the go-ahead, production builds don't leave anything out** (project lead, 2026-11-06, §22). The build has no collection gate: whatever `features` turns on is built, whatever `DATA_COLLECTION` says. So in production before the go-ahead:
  - `events.js` loads on the pages that need it (§10.1) and the privacy page shows the statistics switch.
  - A tab that opens a problem page, Start here or Getting urgent help keeps the visit code in `sessionStorage`, as the privacy page already says.
  - Browsers send their usage beacons, search text included, and the Worker answers 404 without reading the body or logging anything (§14.1). `events.js` ignores the answer. Each beacon still costs one Worker request against the daily limit.
  - Browser devtools list these 404s as failed network requests: checked 2026-11-06 in headless Chrome 157, whose console shows one "Failed to load resource: the server responded with a status of 404 (Not Found)" line per beacon (Firefox and Safari not checked). They aren't script errors, so M7's "without console errors" check must allow for them.
  - The rating widgets (M4) and the feedback dialog (M5) show in production too, and fail with their inline message until the go-ahead: the API's 404 is a failure (below). The only way to hide them is to turn their feature off, which also hides them in previews and locally.
  - **The feedback dialog shows even before a real Turnstile site key exists** (decision A1, project lead, 2026-11-07). While `turnstileSiteKey` is the placeholder, production's dialog loads nothing from Cloudflare and has no field to write in and no Send button: it holds the notice, Close and the message that the spam check isn't working, with a link to the Contact page. So no production visitor can send feedback through it, or write a message that can't be sent, until a PR adds the key (§13, §18.4 step 5). From then on it fails with `SEND_FAILED` until the go-ahead, like the ratings.
  - The go-ahead itself is still a reviewed one-line change to `DATA_COLLECTION` (§18.3). If it comes before launch, production's API still answers on no host, so that PR also decides whether to open it on production's `workers.dev` address through `API_HOSTS` (§21).
- **Locally**, `wrangler dev` and the tests read the top level of `wrangler.jsonc`, so collection is off there too, and `npm run dev` gets the same 404s as production. For a local run with collection on, use `npm run dev:collect` (§18.1). It passes `--var DATA_COLLECTION:on` and `--var API_HOSTS:localhost:8787,127.0.0.1:8787` to `wrangler dev`, for that run only, and `--var TURNSTILE_SECRET:1x0000000000000000000000000000000AA`, Cloudflare's published always-pass test secret, which goes with the test site key the dialog uses there (§13, §14.3). It is no spam check at all: it accepts any token string, not just the test key's dummy token (seen 2026-11-07), which is harmless locally. Never put `DATA_COLLECTION` or `API_HOSTS` in `.dev.vars` or a `.env` file, which `wrangler dev` and the Worker tests also read (a test checks). `TURNSTILE_SECRET` may be set there, but only to one of Cloudflare's three published test secrets (a test checks that too); a real secret lives only in Cloudflare (§18.4 step 5).
- **Runtime failure:** the widgets send through `src/js/api.js`. `postJson(path, data, { keepalive })` POSTs `data` as JSON (`Content-Type: application/json`, credentials left at fetch's default so a preview behind Access keeps its cookie) and resolves to the answer's HTTP status, or `0` when there is none: a network error, no `window.fetch`, or no answer within 5 seconds, when the request is aborted. It never rejects or throws, makes one attempt (no automatic retries), never reads the answer's body and makes no console calls. Only a 2xx status is success. Anything else is a failure: a 3xx, the 404 that production answers until the go-ahead, a 429, a 5xx, and no answer at all. `rating.js` always passes `keepalive: true`, so a rating made just before leaving the page still gets out; `feedback.js` doesn't (a message is sent from an open dialog, not as the page closes). On failure, the widget shows a short inline message ("Couldn't send right now — please try again later", with no full stop: `SEND_FAILED` in `api.js`) and the rest of the page is unaffected. Since the body is never read, the feedback dialog shows it for a failed Turnstile check (`403 turnstile`) too (§13). Event logging doesn't use `api.js`: `events.js` sends beacons, ignores the answers and fails silently (§10.1).
- No widget may cause layout shift or block rendering while waiting for the API. The rating status line's height is reserved before anyone rates (§12), so its answer never moves the page. The feedback dialog is modal and anchored to the top, with its status line last, so its messages only lengthen it downwards and move nothing on the page (§13).

## 12. Ratings widget (`src/js/rating.js`)

- **Where.** Under every video, placeholders included (§7): the problem video and each solution on problem pages, and each intro video on Start here. Ratings are per video. The widget ends the row of controls under each video, after "Audio only" and "Handout" (§7.5, `src/_includes/partials/video-controls.njk`): under the problem video, in each open solution card and under each Start here video. Templates render it from `src/_includes/partials/rating.njk` only while `features.ratings` is exactly `true` (§11).
- **Markup.** A `<fieldset>` whose legend is "Was this helpful?" followed by the video's title in a visually hidden span (a problem page can have up to seven groups), and five native radio inputs styled as stars (so arrow keys move between them), labelled "1 star" to "5 stars", with `autocomplete="off"`. Each star is a 44×44px `<label>`. Unfilled stars have a `slate-grey` outline; the checked star and those before it a `warm-clay` fill with a `clay-deep` outline (a browser without `:has()` fills only the checked one; in forced colours they fill with the system text colour). Then the status line, and nothing else: no notice (project lead, 2026-11-06, §15.1). The widget's root carries `data-rating="<video_id>"`, which `rating.js` sends and `pages.json` reads (§8.3); it is `display: contents`, so the fieldset and the status line are items of the row.
- **Without JavaScript nothing shows.** The widget, and a row of controls that would hold only the widget (`data-rating-reveal`: a video with no handout or audio), ship `hidden`, and `rating.js` reveals them once its listeners are in place (§11). They stay hidden if the script fails or the page has no `data-page-id`. A form POST can't be the fallback: the API takes only JSON (§14.1).
- **Sending.** `POST /api/rate { page_id, video_id, stars }` through `api.js`, with `keepalive` (§11); `stars` is a JSON number. The body holds nothing else: no `session_id` (`rating.js` never reads `sleepsteps-visit`). A rating dispatches no `sleepsteps:event`, so it writes no events row, and it ignores the usage statistics switch (§10.1).
  - **When** (decision a1 = B, project lead, 2026-11-06). A star chosen by pointer, touch, Space or a screen reader's activation (all of them clicks) is sent at once. A star reached with an arrow key is held, because native radios check every star the arrows pass, and is sent on the first of: 2 seconds without another change, focus leaving the group, Enter, or `pagehide`. A held star equal to the last rating the API accepted isn't sent again, so arrowing away and back adds no row; the status line then gives the thanks for it (below). An arrow key pressed with Alt, Ctrl or Meta doesn't count as arrowing, and a pointer press clears it. Very slow arrowing (more than 2 seconds a step) can still store the stars passed on the way. `HOLD_ARROW_KEYS` and `HOLD_MS` in `rating.js` hold the decision.
  - **A click after arrowing.** A press (mouse, pen or touch) on a star drops a held star, and the clicked star is sent at once, alone. Browsers blur the focused radio when a star's label is pressed, before the click (Chrome: `pointerdown`, `mousedown`, `focusout` with no `relatedTarget`, then the click; with touch, `pointerup` comes before the `mousedown`), so from `pointerdown` on a star (its `<label>` or radio) until the next click, a `focusout` with no `relatedTarget` doesn't count as focus leaving the group, and the hold's timer waits. `pointerup` restarts the timer, so a press that ends off the stars (its click lands on the fieldset) still sends the held star 2 seconds later; `pointercancel` restarts it too and ends the press. Clicking the star that is already checked fires no `change` event: if it is the held star (pressed, or a screen reader's activation), it is sent then. Space on the held star sends it too, on `keydown`, as Enter does: Chrome and Safari fire no click for Space on a checked radio (checked in headless Chrome on the built page). Clicking the checked star, or Space on it, with nothing held sends nothing. Arrow keys also fire a click on the star they check, before its `change`, which is always a different star from the held one, so it sends nothing.
  - **One request at a time per widget, newest wins.** A star chosen while a request is in flight waits, replacing any star already waiting, and is sent when that request ends unless it is the star just sent. So a choice replaced while an earlier one was in flight is never sent, and the rows arrive in the order chosen. If the page is hidden while a request is in flight, the newest waiting star (held or queued) is sent at once, without waiting for the answer, unless it is the star in flight, and it becomes the newest request.
  - **Only the newest request's answer counts.** If the page comes back from the back/forward cache, the older request's answer, whichever comes first and whether or not it succeeded, changes nothing: it doesn't set the accepted rating, the status line or the stars. So a later choice equal to the older star is still sent, since the accepted rating is the newer one.
- **Status line**, on its own line under the row of controls. It stays when everything else is pulled back (project lead, 2026-11-06): keyboard and screen-reader users need to hear that a rating was stored or failed. It becomes `role="status"` when `rating.js` starts, so nothing is announced on load.
  - **Before a rating it is empty** (decision a2 = B, project lead, 2026-11-06; the alternative was "Ratings are anonymous.", which the §15.1 notice then under it repeated, and that notice is gone too). Its height is reserved by hidden copies of the two longest messages in the same grid cell, so an answer never moves the page (§11); the cost is a blank line under the row (two on a narrow phone) before anyone rates. `READY_TEXT` in `rating.js` holds the decision.
  - While sending, nothing visible changes apart from the checked star, and the radios are never disabled (which would lose focus).
  - **Success** (2xx): "Thanks. You rated this 4 of 5." Nothing else on the page shows the rating: a closed solution card has no summary line (project lead, 2026-11-06).
  - **Failure** (§11): "Couldn't send right now — please try again later", and the stars go back to the last rating the API accepted, or none, so a filled star means a recorded one and picking any star retries.
  - The status changes only once no newer star is waiting or held, so it always matches the checked star: the newer star's own answer reports instead, and an older failure is then neither shown nor reverted. When a held star ends (its 2 seconds, focus leaving, Enter, Space, a click on it or `pagehide`) with no request in flight and it is the rating the API last accepted, nothing is sent and the status line shows "Thanks. You rated this n of 5." unless it already does: for example, click 4, arrow to 5 and back to 4 while the 4 is in flight; the 4's answer comes while 4 is held, so the thanks for 4 shows when the hold ends. A message equal to the one shown is cleared and set again 100 ms later, so it is announced again.
- **Changing and coming back.** The user may change the rating, and each change is a new row; duplicates are acceptable. Nothing is stored on the device (no §15.4 row), and `rating.js` unchecks every radio when it starts, so a browser restoring form state can't show an earlier choice and a returning visitor's earlier rating is not shown.
- No notice under the widget (project lead, 2026-11-06, §15.1): the privacy page covers ratings (§15.2).
- No aggregate score is displayed.

Built in M5 with the project lead's decisions of 2026-11-07: A1 (the dialog shows in production before a real Turnstile site key exists), A2 (after a success the dialog stays open), A3 (the stored time is rounded to the hour, §14.2), A4 (the dialog is on the search page too, and Turnstile's view of the address is disclosed) and A5 (the draft wording below) (§22).

- **Where.** A "Send feedback" item in the footer, which is on every page (Getting urgent help included since 2026-11-07, §7.4), opens a modal `<dialog>`. This is the only feedback entry point; there are no per-video feedback forms (§7.5).

Once its listeners are in place, `feedback.js` swaps the link for a `<button type="button">` of the same look (no layout shift) and unhides the dialog. The item stays a link to the Contact page (§15.2) without JavaScript, without `<dialog>` support, if the script fails, and on the 404 page; if the dialog can't open, the button goes there too. A page without a `page_id` never sends feedback, so no path is ever sent (§14.2 accepts only a `page_id` in `pages.json`).
- **Markup**, in this order: the heading "Send feedback" (an `h2` with `tabindex="-1"`, which labels the dialog); the §15.1 notice, which describes it; the label "Your message" and a `<textarea maxlength="2000" autocomplete="off">` whose `aria-describedby` is the hint "Up to 2,000 characters." (the three in one `div` with `data-feedback-field`, so they can be hidden together); the box Turnstile renders into; Send (`type="submit"`) and Cancel; and the status line. The form has `method="dialog"` and `novalidate`, and the textarea has no `name`, so a native submit (if the script's handler ever failed) only closes the dialog, and the message can never end up in an address. No inline style or script (§16.1).
- **Focus and keyboard.** Opening calls `showModal()` and moves focus to the heading, not the textarea, which on phones would raise the keyboard over the notice. Focus order: heading, textarea, Turnstile's widget, Send, Cancel, then the Contact link in the status line when there is one. Escape, Cancel or Close close the dialog and return focus to the footer button, unless focus has already moved elsewhere on the page. Known limitation: Escape does nothing while focus is inside Turnstile's widget, a frame from another origin whose key presses never reach the page (seen in Chrome 157, 2026-11-07); Tab or Shift+Tab leaves the frame (it is no keyboard trap), and Escape works from there. The page can't fix this. The draft is kept in memory across Cancel and Escape (never stored anywhere) and cleared after a success. No `aria-haspopup`, and no `tabindex` on the `<dialog>`. With no usable site key (A1, below) the focus order is the heading, Close, then the Contact link.
- **The status line** is the dialog's last element. It becomes `role="status"` when `feedback.js` starts, so nothing is announced on load. Messages only make the dialog longer downwards, so nothing above them moves. After Send, the dialog scrolls, if it must, to show the line (on a phone it is below the buttons); apart from keeping the focused control in view above an on-screen keyboard (below), nothing else scrolls it. A message equal to the one shown is cleared and set again 100 ms later, so it is announced again. A message the dialog opens with (the spam check has failed, "Sending…", or an answer that came while it was closed) is also written 100 ms after opening: a closed dialog's live region isn't in the accessibility tree, and one that appears together with its text may not be announced (M5 review, 2026-11-07). Closing clears the line, except "Sending…"; an answer that arrives while the dialog is closed still applies, and shows when it next opens. The wording is in `MESSAGES` in `feedback.js`; `SEND_FAILED` is fixed by §11 and the thanks by this section, and the rest are drafts for the lead (A5), the HREC and the privacy officer (§15):

  | State | Status line, and what else happens |

  | The text reaches 2,000 characters | "You've reached the 2,000-character limit.", once each time it gets there (`maxlength` cuts a long paste off silently). No live counter, which would be noisy for screen-reader users |

- **Sending.** `POST /api/feedback { page_id, message, turnstile_token }` through `api.js` (§11), exactly those keys: `page_id` from `<body data-page-id>`, the textarea's value as typed (the Worker cleans and checks it, §14.2) and the widget's token. No `page_title` (the Worker takes titles from `pages.json`), no `session_id` and no `keepalive`. After every answer the token is spent (tokens are single-use), so the widget that gave it is reset for a new one. `api.js` never reads the body, so a `403 turnstile` can't be told from the origin check's 403, and both get `SEND_FAILED`.
- **Turnstile** (Cloudflare's spam check; §14.3, §15.4, §16.2):
  - **Loaded on the first open only.** `feedback.js` appends `https://challenges.cloudflare.com/turnstile/v0/api.js?render=explicit`, the exact URL Cloudflare gives, with `async`, once per page, and renders from its `load` event: no `turnstile.ready()` (which throws for an `async` script), no global `onload` callback, no preconnect, no SRI and no self-hosted copy (Cloudflare: "Proxying or caching this file will cause Turnstile to fail when future updates are released"). Nothing contacts Cloudflare before the dialog first opens: a build test checks that no built page names `challenges.cloudflare.com`, and a source test that only `feedback.js` does, with exactly that URL.
  - **Rendered on each open and removed on each close** (`turnstile.remove`), so no token refreshes reach Cloudflare while the dialog is closed. The box is measured just before rendering: `normal` (300×65) when it is at least 300px wide, otherwise `compact` (150×140). Its height is reserved at that size, so the widget never moves the buttons.
  - **Render options**, pinned by a test as the exact set: `sitekey`; `action: 'feedback'` (it labels Cloudflare's analytics and is never checked); `theme: 'light'`; `language: 'en'`; `size`; `appearance: 'always'`; `'response-field': false` (the token goes in the JSON body); `'feedback-enabled': false` (it "allows Cloudflare to gather visitor feedback upon widget failure", which the notice doesn't cover); and `callback`, `'expired-callback'`, `'timeout-callback'`, `'error-callback'` and `'unsupported-callback'`. The error callback returns `true`, so Turnstile logs nothing to the console (§20 M7). Never `cData`, and never `session-continuity-persist`, which would write `_cftscs_<sitekey>` to this site's own `localStorage` (§15.4).
  - **The site key is chosen at run time** (§11): Cloudflare's visible always-pass test key `1x00000000000000000000AA` on `localhost`, `127.0.0.1`, `[::1]` and preview and version hosts (`<alias or version>-sleepsteps.<subdomain>.workers.dev`); elsewhere the dialog's `data-sitekey` (`turnstileSiteKey`), if it is a real key (`0x…`). Cloudflare's test keys work on any domain, but production's secret refuses the dummy token they give, so the test key gains nothing on a version URL, whose API answers 404 anyway (§14.1). Production can't use the test key: its widget says "For testing only. If seen, report to site owner".
  - **No usable key** (the placeholder, in production; A1 = show the dialog anyway). The dialog still opens, but `feedback.js` loads nothing from Cloudflare (no request, no `cf.turnstile.u`, no console warning for an invalid key) and hides the field (label, textarea and hint, in their `data-feedback-field` wrapper), the widget's box and Send, so nobody writes a message that can't be sent; Cancel reads "Close". The dialog holds the heading, the notice, Close and the spam-check message with the Contact line, written just after it opens and, with nothing else below Close, in view on a phone (M5 review, 2026-11-07). This lasts until a PR adds the real key (§18.4 step 5).
- **Look.** Paper ground, ink text, a deep-teal focus ring and a 1px keyline border (visible in forced colours), no shadow or animation and no scroll lock; at most the text measure wide, anchored near the top, and scrolling within itself when taller than the viewport. A scroll that starts in the dialog stays in it (`overscroll-behavior: contain`) instead of carrying on to the page once the dialog reaches its end; the page behind still scrolls, so this is no scroll lock. The backdrop is `--backdrop` (ink at 60%, declared on `::backdrop` in `tokens.css`, since in some engines it inherits nothing), the textarea is 17px (iOS zooms in on smaller text) with a slate-grey border, and Cancel is the outlined button (`.button--outline` in `components.css`: deep-teal text and border on paper). Send and Cancel share a row at every width (project lead's phone test, 2026-11-07): on phones each grows from 7rem to half the row (123px each at 320px, 158px at 390px), so they take one 52px row instead of two, and stack again only when there is no room (very large text); from 600px they keep their own width. Alone (Close, with no usable key), the button fills the row on phones. The styles are in `site.css`, with the footer's; the dialog is hidden in print.
- **Above an on-screen keyboard.** iOS Safari, and Chrome on Android by default (`interactive-widget=resizes-visual`), shrink only the visual viewport when the keyboard opens, and the dialog is fixed to the layout viewport, so its lower part (the spam check, Send, Cancel and the status line) stayed behind the keyboard, where scrolling the dialog couldn't lift it (the project lead's phone test, 2026-11-07). While the dialog is open, `feedback.js` follows `window.visualViewport`'s `resize` and `scroll` events. While the visual viewport is more than 1px shorter than `window.innerHeight` (a smaller gap is only `innerHeight`'s rounding to whole pixels: at 125% display scaling Chrome gives 705.6 against 706, which would otherwise move a desktop dialog) and not pinch-zoomed (scale within 0.01 of 1), it sets `--feedback-visible-top` and `--feedback-visible-height` on the dialog (the viewport's `offsetTop` and `height` in whole pixels, written only when they change). `site.css` then puts the dialog a gutter below the top of the visible area, at most the visible height less two gutters (16px, or 24px from 600px, instead of 40px). When zoomed in, at full height and on closing, it removes them and its listeners, so the dialog goes back to its usual place and a reader of a magnified page pans as before. Without `visualViewport` nothing changes. A fit that makes the dialog shorter keeps the focused control (the textarea, as the keyboard opens) in view, 8px clear of the dialog's edges, by scrolling the dialog itself and never the page, whose scrolling would move the visual viewport and so the fit. The properties are set through the CSSOM (`style.setProperty`), which `style-src 'self'` doesn't block (§16.1). A source test allows `.style` in `feedback.js` only to set and remove those two properties. Checked in headless Chrome 157 with a stand-in visual viewport (340px visible at 390×844, 330 at 360×780, 260 at 320×568): the dialog stayed inside the visible area and scrolling it alone brought the spam check, Send and Cancel into view; iOS Safari and Android need a real phone.
- **Never:** console calls, device storage, a `sleepsteps:event` (feedback writes no events row and ignores the usage statistics switch), reading `location.search`, `turnstile.ready()`, or putting the message anywhere but the request body.

## 14. Worker API

### 14.1 General rules (all `/api/*` routes)

`worker/router.js` checks every `/api/*` request in this order, and the first check that fails answers:

| # | Check | Answer |
|---|---|---|
| 1 | `DATA_COLLECTION` is exactly `"on"` (§11) | `404` |
| 2 | The request's host (`new URL(request.url).host`, with its port) matches `API_HOSTS` (below) | `404` |
| 3 | The path is a route (exactly: `/api/event`, `/api/rate` or `/api/feedback`, so `/api/rate/` and `/api/Rate` are not), and its feature is exactly `true` in `site.config.json` | `404` |
| 4 | The method is `POST` | `405 method`, with `Allow: POST` |
| 5 | The `Origin` header is exactly the request's own origin (`new URL(request.url).origin`), so a missing Origin, `null`, another site, or `http:` for an `https:` page is refused | `403 origin` |
| 6 | The media type (the part of `Content-Type` before `;`, trimmed and lowercased) is `application/json` or `text/plain` (sendBeacon's) | `415 content_type` |
| 7 | The raw body is at most the route's limit: 4096 bytes for `/api/event` and `/api/rate` (`MAX_BODY_BYTES`), 16384 for `/api/feedback` (`MAX_FEEDBACK_BODY_BYTES`: a 2048-character Turnstile token with a 2000-unit message comes to about 4.1 KB in ASCII, 8.1 KB in three-byte characters and 14.1 KB at worst, with control characters escaped as `\u00XX`). A `Content-Length` over the limit is refused without reading, and the body is also counted as it streams (one sent without `Content-Length`, or longer than declared), stopping at the first byte past the limit | `413 too_large` |
| 8 | The body is UTF-8 (a strict decoder) and JSON (`JSON.parse`; `request.json()` is never used) | `400 body` |
| 9 | The route's own rules (§14.2); for `/api/feedback`, then Turnstile's check (§14.3); then its D1 write | `400` with the failed rule's code, `403 turnstile` (feedback), or `204` |

So a cross-site request is refused before its body is read. Anything unexpected in steps 7–9, a failed D1 write included, answers `500 server`. No CORS headers are needed (same origin).

- **`API_HOSTS`** (`worker/lib/hosts.js`) is a Worker var in both blocks of `wrangler.jsonc`: comma-separated host patterns for the hosts the API **and the admin pages** (§14.4) answer on, where `*` stands for letters, digits and hyphens within one DNS label. An entry with any other character matches nothing, so the `"<DOMAIN>"` placeholder matches no host, and neither does a missing value.
  - **Production:** `"<DOMAIN>"` until launch, so production's API and admin pages answer on no host at all, `workers.dev` and version URLs included. The launch PR sets it to the domain, together with `siteUrl` (§18.3).
  - **Previews:** `"*-sleepsteps.*.workers.dev"`, every preview URL. Only previews read that block, so production's version URLs, which have the same shape, run with production's value and never match.
  - **Locally:** `localhost:8787,127.0.0.1:8787`, from `npm run dev:collect` (§11). The admin pages still answer 403 there, since the `ACCESS_*` vars are placeholders and there is no way to skip Access (§14.4).
  - **Invariant: every host in a block's `API_HOSTS` is behind a Cloudflare Access application that covers `/admin` and `/admin/*`**: production's domain by the `/admin` application, preview URLs by the Worker-level "Previews only" application (§14.4, §18.4 step 6). The admin pages answer 403 on any other host, so production's version URLs, and before launch its `workers.dev` address, never serve them. A PR that adds a host here first needs Access to cover that host's `/admin` paths, and §18.4's smoke test checks each listed host.
- **Responses.**
  - Success is `204` with no body.
  - Errors are `{"error":"<code>"}` with `Content-Type: application/json; charset=utf-8`. The codes are a closed list (`ERROR_CODES` in `worker/lib/http.js`): `body`, `type`, `page`, `session_id`, `detail`, `video`, `stars`, `message`, `turnstile`, `origin`, `content_type`, `too_large`, `method`, `server`. M4 added `video` and `stars`, and M5 `message` (400) and `turnstile` (403).
  - Every 404 is the plain `Not found` of the rest of the site, so collection being off, a host that isn't allowed, an unknown route and a disabled feature all look the same.
  - Every API response, 404s included, carries `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`.
  - `403 turnstile` is also the answer for a failed Turnstile check (§14.3), and `500 server` for a missing `TURNSTILE_SECRET` or a Siteverify that can't answer. `429` comes from the Cloudflare rate-limiting rule, which covers only the custom domain (§16.3).
- **Time.** Timestamps are set by the server, as ISO 8601 UTC with milliseconds (`toISOString()`). A client's time is never read: a `ts` key in the body is refused. Free text from anyone is stored with `ts` rounded down to the hour, so it is hard to match to the same visit's other rows by time: `search` events (§10.1) and feedback (decision A3, project lead, 2026-11-07). Both use `hourTimestamp()` in `worker/lib/time.js`. Ratings keep the exact time: a rating holds no free text, so linking it to a visit by its time reveals only a star count (§22).
- **Pages.** Check `page` against `worker/generated/pages.json` (§8.3), which lists every page with a `page_id` (`home` and `search` included). Store titles from `pages.json`, never from the client.
- **Never store or log** IP addresses, user agents, `CF-Connecting-IP`, or feedback/search text in `console.log` (Workers Logs).
  - No route reads `User-Agent`, `Referer` or `request.cf`. `CF-Connecting-IP` is read by the router alone, and only for `/api/feedback` (`remoteIp: true` in its `ROUTES` entry): the router passes it, or `null`, to that handler only, in a fourth argument, and the handler sends it to Siteverify as `remoteip` (§14.3), never storing or logging it. The event and rate handlers are called with three arguments, so they can't see it (their fourth is the `now` the tests pass). `test/node/worker-source.test.js` checks these reads and pins every console call in `worker/`.
  - Log lines are fixed strings. They never contain the request's address, headers or body, nor an error's message: V8's JSON errors quote the input, and D1's messages can echo bound values. A failed D1 write logs a fixed message and the error's `D1_…` code only (`<route>: database write failed` and the code, or `unknown`). Every error is caught, since an uncaught one would reach the logs with its message.
  - Workers Logs (`observability`) is off in both blocks of `wrangler.jsonc`, because invocation logs record request metadata. `wrangler tail` still shows live logs when debugging.
- **D1.** Use parameterised queries only (`prepare().bind()`), binding `null`, never `undefined`. The write is awaited, not left to `ctx.waitUntil`, so a failed write answers 500. The routes write through `insertRow()` in `worker/lib/d1.js`, which holds that log line, so it can't drift between routes.

A search: `session_id` NULL, `ts` rounded down to the hour, `q` trimmed and made well-formed (`toWellFormed()`) |
| `GET /admin/?from=YYYY-MM-DD&to=YYYY-MM-DD` (and `HEAD`) | — | The host is in `API_HOSTS`; a valid Access JWT (§14.4); `from` and `to` UTC days, at most 92 days, `to` not after today (either or both may be left out) | HTML summary (§14.4); 400 with the form, an error summary and no data for a bad range |
| `GET /admin/export?table=ratings\|feedback\|events\|searches&from=YYYY-MM-DD&to=YYYY-MM-DD[&paged=1[&type=…&ts=…&skip=…]]` | — | The same host and Access checks; an allowed table; both dates or neither (the previous UTC month); complete days only (`to` ≤ yesterday); at most 31 days and 100,000 rows; a valid cursor | One CSV file, a "download in parts" page, or one part (`paged=1`) (§14.4); 400 with a fixed plain-text message otherwise. `events` and `searches` never have an `id` column |

Every `/admin` path and method first passes the host and Access checks (403 `Forbidden` for either, before any D1 read). Then any method but `GET` or `HEAD` answers 405 (`Allow: GET, HEAD`); `/admin` answers 308 to `/admin/`, keeping the query; `HEAD /admin/export` answers 405 (`Allow: GET`) without reading D1; and any other path answers 404 (§14.4).

### 14.3 Turnstile verification (`worker/lib/turnstile.js`)

`POST https://challenges.cloudflare.com/turnstile/v0/siteverify`, form-encoded, with `secret` (`env.TURNSTILE_SECRET`), `response` (the token) and `remoteip`, the last only when the request has a non-empty `CF-Connecting-IP` header (never `X-Forwarded-For`). The IP is used for this check only, and never stored or logged (§14.1).

- **One attempt, within 3 seconds** (`SITEVERIFY_TIMEOUT_MS`), counting the time to read the answer, with no retry and so no `idempotency_key` ("A UUID you generate to safely retry validation requests"). The browser gives up after 5 seconds (`TIMEOUT_MS` in `api.js`, §11), and a source test keeps `SITEVERIFY_TIMEOUT_MS + 1500 ≤ TIMEOUT_MS`, so the Worker answers first: a message that was stored is never shown as failed and sent again. Cloudflare: "Set reasonable timeouts. Do not wait indefinitely for Siteverify responses." A token is valid for 300 seconds and can be checked only once.
- **Fail closed.** Only a 2xx answer whose JSON has `success` exactly `true` passes (the string `"true"` doesn't). A missing `TURNSTILE_SECRET` answers `500 server` before any call, logging `/api/feedback: TURNSTILE_SECRET missing`. Otherwise:

  | Siteverify's answer | `/api/feedback` answers | Log line (fixed text and a code from a closed list) |
  |---|---|---|
  | 2xx with `success: true` | the D1 write (§14.2) | none |
  | `error-codes` naming `missing-input-secret`, `invalid-input-secret` or `bad-request` (checked first, since a wrong secret makes every token fail too) | `500 server` | `/api/feedback: siteverify refused the request` and that code |
  | `error-codes` naming `internal-error` | `500 server` | `/api/feedback: siteverify unavailable` and `internal-error` |
  | `error-codes` holding only `invalid-input-response`, `timeout-or-duplicate` or `missing-input-response` (whatever the status), or a 2xx with no codes at all | `403 turnstile` | none |
  | No answer within 3 seconds; a network error; a body that isn't a JSON object, or whose `error-codes` isn't a list; a non-2xx status naming no code (even with `success: true`); an unknown code | `500 server` | `/api/feedback: siteverify unavailable` and `timeout`, `network`, `bad-response` or `other` |

- **No hostname, action or cdata check.** Cloudflare: "A successful validation with a test secret key always returns example.com as the hostname, and the response does not include action or cdata", so checking them would break local runs and previews. The widget's hostname list, the Origin check and `API_HOSTS` (§14.1) already limit where a token can come from.
- **The secret.** Production's is set by a person with `wrangler secret put TURNSTILE_SECRET` (§18.4 step 5); without it, every feedback request answers `500` once collection is on. Previews get Cloudflare's always-pass test secret as a base secret, needed only once their collection is on (§21), and `npm run dev:collect` passes it with `--var` (§11). Cloudflare says test secrets "only accept the dummy token" that test site keys give, but in a local run on 2026-11-07 the always-pass secret also accepted a made-up token (`not-the-dummy-token`, 204 and a stored row). So wherever that secret is set, Turnstile stops nothing: on previews with collection on, Cloudflare Access is the only gate (§21). What keeps production safe is the other half: "production secret keys will reject the dummy token", so the run-time choice of the test key on local and preview hosts (§13) can't let anything through there. There is no server-side guard against a test secret in production; instead §18.4 has a `curl` check that production's secret refuses the dummy token, and a real message sent through the dialog to show it is the widget's own secret. `wrangler.jsonc` has no `secrets.required` (Wrangler would fail every build and deploy until a person had set the secret) and no var named `TURNSTILE_SECRET` (Cloudflare: "Secrets cannot be stored in Wrangler configuration files"); a test checks both.
- **In the tests**, Siteverify is never contacted: the Worker tests replace `globalThis.fetch` (`vi.spyOn`), answer only `SITEVERIFY_URL`, and fail on any other fetch (`@cloudflare/vitest-plugin` 1.4.8 has no `fetchMock`).

### 14.4 Admin

Staff-only pages (M6): a summary page at `/admin/` and CSV exports at `/admin/export`. They only read. Built as the project lead decided on 2026-11-07 (decisions B1–B5, §22).

- **Access at the edge.** `/admin` and `/admin/*` are protected by Cloudflare Access (dashboard configuration, §18.4 step 6), with two reusable policies that list named emails only, never a whole email domain (decision B4):
  - **Production:** a self-hosted application for the domain that lists **both** paths, because `admin/*` alone does not cover `/admin`, with the **"data access"** policy: the research staff the HREC and the privacy officer are told can see the data.
  - **Previews:** the Worker-level "Previews only" application, with the separate **"preview reviewers"** policy (everyone who reviews previews). So reviewing a preview never gives access to production's feedback and searches. Production's `ACCESS_AUD` is only ever the AUD of an application whose policy is "data access".
- **Invariant: every host in a block's `API_HOSTS` is behind an Access application that covers `/admin` and `/admin/*`** (§14.1). The Worker's host check (below) relies on it: on a host Access doesn't cover, the Worker alone would accept a valid token replayed from a staff member's browser, which Access's binding cookie stops only at its edge. §18.4 step 6 checks it on every listed host: a request with no cookie gets a 302 to the team's sign-in.
- **The Worker runs first** for both paths (`run_worker_first`, §18.2). Otherwise a browser opening `/admin/` gets the static 404 page without the Worker running.
- **The Worker's own checks, in this order, for every `/admin` path and method** (`worker/routes/admin.js`). The first two are gates: a failure of either answers the same plain `403 Forbidden`, whatever the path or method, and nothing reads D1 before both pass (a test wraps `env` to prove it). Anything unexpected inside them (a throw) answers 403 too: the gates fail closed.
  1. **The host is in `API_HOSTS`** (§14.1). So production's version URLs, which run production's code on its database, and production's `workers.dev` address before launch, never serve the admin pages. (This host gate is the default the M6 PR proposes; the project lead may still overrule it, §21.)
  2. **A valid Access token** (`worker/lib/access-jwt.js`), defence in depth behind Access:
     - `ACCESS_TEAM_DOMAIN` is `<name>.cloudflareaccess.com` (no scheme) and `ACCESS_AUD` is 64 hex characters, so the `<TEAM>` and `<AUD_TAG>` placeholders refuse everything and fetch nothing;
     - the token is read from the `Cf-Access-Jwt-Assertion` header only, never the `CF_Authorization` cookie (Cloudflare recommends the header). It has at most 8,192 characters, in three base64url parts with a non-empty signature, whose header and payload are UTF-8 JSON objects;
     - the header's `alg` is exactly `RS256`, with no `crit` member, and `typ`, if present, is `JWT`; `jku`, `x5u` and `jwk` are ignored, so a key the token names is never fetched or trusted;
     - the claims: `iss` exactly `https://<ACCESS_TEAM_DOMAIN>`; `aud` is `ACCESS_AUD` or a list that includes it; `type` is `app` (an `org` token is a global session); `exp` is a number, and `exp`, and `nbf` and `iat` if present, are within 60 seconds of now. These checks need no I/O, so a garbage token never causes a fetch;
     - the `kid` is a key in the team's certs (`https://<ACCESS_TEAM_DOMAIN>/cdn-cgi/access/certs`, its `keys` list of JWKs, never `public_cert`), and the RSASSA-PKCS1-v1_5 SHA-256 signature verifies.

     The check returns only "ok" or a failure code. It reads no claim beyond these, and never the email.
  3. **The method:** any but `GET` or `HEAD` answers 405 (`Allow: GET, HEAD`).
  4. **The path, exactly:** `/admin` answers 308 to `/admin/`, keeping the query; `/admin/` is the summary; `/admin/export` the export; anything else 404. `HEAD /admin/` runs the summary and drops the body; `HEAD /admin/export` answers 405 (`Allow: GET`) without reading D1, since a download is only ever a GET. The URL parser resolves dot segments first, so `/x/../admin/` reaches these checks; `/%61dmin/`, `//admin/` and `/admin%2Fexport` are not admin paths and go to static assets (tests cover both).
  5. **`/admin/export` only: the download started on the admin pages.** A `Sec-Fetch-Site` header other than `same-origin` (the summary's links, the download page's fetches) or `none` (a typed address or a bookmark) answers 403 with a fixed plain text ("Start the download from the admin page: open /admin/ and choose it there."), before D1 is read, and logs nothing; a browser that sends no header passes. Otherwise another website could make a signed-in staff member's browser run downloads: each is a top-level GET, which carries the Lax `CF_Authorization` cookie, and its attachment leaves that site's page open to start the next, so a loop could use up the account's daily D1 reads (below). The summary isn't checked: the redirect back from the Access sign-in arrives as `cross-site`, and an HTML answer replaces the page that navigated, so the other site can't repeat it. The cost: an export link opened straight after signing in again is refused once.
- **Keys.** The verifier caches imported keys in memory, one cache per isolate (never a pending promise; the Cache API isn't available behind Access). A key fetched under an hour ago is used as it is. A stale cache or an unknown `kid` fetches the certs again, at most every 30 seconds once keys are held or a fetch has failed (before the first fetch succeeds every request fetches, so two first requests on a new isolate don't refuse each other). A fetch has 3 seconds, body included, and a body over 64 KB is refused. A fetch that fails keeps the old keys, usable for up to 24 hours (Access rotates its key every 6 weeks and keeps the previous one valid for 7 days). With no usable key the answer is 403 and one fixed log line. There is no JWT library: Cloudflare doesn't pass `ctx.access` to a Worker with static assets, and `access.dev` in the Wrangler config only simulates it, so `wrangler.jsonc` has no `access` key (a test checks).
- **If Access doesn't pass the header.** That Access sends `Cf-Access-Jwt-Assertion` to a Worker with static assets is UNVERIFIED in Cloudflare's docs; the preview check confirms it (§18.4 step 6c). If it doesn't, every admin request answers 403: closed, never open. The fallback would be to check the same token from the `CF_Authorization` cookie, which needs a change to this section and to `worker-source.test.js`'s list of the headers the Worker reads (§21).
- **No other gates.** Admin doesn't depend on `DATA_COLLECTION` or `features`: it only reads, it must work before the go-ahead (empty tables, previews), and stored data must stay readable after collection or a feature is switched off (§19.3). While `DATA_COLLECTION` isn't exactly `"on"`, the page says so.
- **No bypass.** The deployed Worker has no way to skip Access: there is no bypass var or script. The tests pass their own verifier or certs fetcher to `createRouter`, `worker/index.js` is pinned to `createRouter({ pages, site })`, and Claude's local end-to-end checks use a scratch harness outside the repo that signs its own tokens, with a scratch database (a source test pins `index.js` and forbids `ADMIN_DEV`, `bypass` and `skipAccess` in `worker/`).
- **Dates are UTC calendar days** (decision B2, project lead, chosen over the recommended Melbourne days). `from` and `to` are written `YYYY-MM-DD`, in 2026–2099, and `to` is included: a range runs from `from`'s 00:00:00.000Z to 00:00:00.000Z on the day after `to`, compared as ISO strings with the stored `ts`. A UTC day starts at 10:00 in Melbourne (11:00 in daylight saving). Every date and time the pages show says UTC, and there is no time-zone code (`worker/lib/date-range.js`). Exported `ts` values stay as stored.
  - **The summary:** both dates left out means the 30 days ending today; `to` alone, the 30 days ending on `to` (never before 2026-01-01); `from` alone runs to today. `from` must be on or before `to`, `to` not after today, and the range at most 92 days (`MAX_SUMMARY_DAYS`, decision B3). Otherwise the answer is 400: the form again, with an error summary linking the field at fault, and no data. A raw parameter is never echoed: the date fields show only dates that passed.
  - **An export:** both dates left out means the previous UTC calendar month; one alone is a 400. Downloads cover complete days only (`to` ≤ yesterday), so the monthly files follow each other with no gap and every row in a range is final while its parts are fetched. At most 31 days (`MAX_EXPORT_DAYS`) and 100,000 rows (`MAX_EXPORT_ROWS`) per download (decision B5, below). Each failure is a 400 with a fixed plain-text message that never quotes the request.
- **The summary page** is rendered by the Worker (`worker/lib/admin-page.js`; §3), with no script. For the range it shows:
  - page views and visits (distinct `session_id`) per tracked page (problem pages, Start here and Getting urgent help, the `pages.json` entries with `page_view: true`, §10.2), every tracked page listed, those with no views included, plus a page no longer in `pages.json` by its id; and the total views and distinct visits. Visits that touch only other pages are not counted;
  - the rating count and mean (to one decimal place) per video, per page, and per page and video. They count ratings, not people: a changed rating is a new row;
  - how many searches there were and how many found nothing, and the 20 most frequent zero-result searches, grouped ignoring ASCII capitals (SQLite's `lower()`), ties broken by text;
  - the 20 most recent feedback messages, ordered by `ts` and then `id`, newest first, with the range's total. Each shows its page's title (its page id when the title is empty) and its hour in UTC (`ts` is rounded down to the hour, §14.1), and the message as stored, in an element with `dir="auto"`;
  - media plays per item, separately for videos and audio-only versions. A play is one (`session_id`, page, item) group at its highest `furthest`, counted as under 25%, 25%, 50%, 75% or 100%, so the five counts add up to the plays;
  - handout clicks, and the visits that clicked, per item;
  - download links: last month's four files, and the range's complete days, split at month ends when the range is longer than 31 days. Every heading and link names its days as UTC ("Ratings, October 2026 UTC (CSV)"), and a note under "Last month" says a month's files are ready from 00:00 UTC on the 1st of the next month (10 or 11 am in Melbourne);
  - the rows the page read (the sum of D1's `meta.rows_read` for its batch). Over 500,000, a tenth of the free plan's daily reads, the footer asks staff to choose shorter ranges and tell the developer, since `MAX_SUMMARY_DAYS` may need to come down (decision B3, §17).

  Every table has a fixed order on its content (counts first, then title or id), so the same rows give the same page whatever their ids. Videos are shown by `video_id`, not title. The page shows exact counts: whether small counts are suppressed applies to reports shared outside the team, a question for the privacy officer (§21). It never shows `events.id`, `session_id`, `feedback.id` or `ratings.id`. All of it comes from one D1 batch (one transaction, so one consistent snapshot, counted as one query). If that fails, a `sqlite_master` check tells "The database isn't set up here yet" (the tables are missing) from "Couldn't read the database"; both answer 500 with the form. The page header shows the host, so production can be told from a preview's test database, and a Sign out link (`/cdn-cgi/access/logout`). The page links to no public page: a staff member's click would add a `page_view` to the data being read.
- **Exports: four tables** (decision B1, project lead), with these columns and orders:
  - `ratings`: `id, ts, page, video, stars`, by `ts, id`;
  - `feedback`: `id, ts, page, page_title, message`, by `ts, id`;
  - `events`: `ts, session_id, page, type, media, furthest`, the usage events only: by type (`page_view`, `video_play`, `audio_play`, `handout_open`), then `ts, page, session_id, detail`. It holds no free text, but it is still research data, handled under the ethics approval (§15.3);
  - `searches`: `ts, q, results`, from the `search` rows of `events`, by `ts` and then the stored detail, so searches within one hour sort by their text, never by id.

  Ratings and feedback keep their `id`: each table has its own sequence, not interleaved with `events.id` (§15.3), which helps remove duplicates across files and find a row to delete. Without `AUTOINCREMENT`, a deleted highest row's id can be reused. An event's `detail` is never exported raw: it is split into columns, and every key of every stored detail shape has one (a test checks).
- **Parts.** Workers Free allows 10 ms of CPU per request, and D1 refuses a result over 50 MB, so a request builds one part whole in memory: up to 2,000 rows (500 for feedback), with one query per event type and a keyset cursor `(type, ts, skip)` (the `ts` of the last row sent, and how many rows with exactly that `ts` were sent). The cursor holds no id and no free text. Its `skip` relies on complete days: no row can join a group with the same `ts` while the parts are fetched.
  - A download that fits in one part is one CSV file, straight from the summary page's link, with no script.
  - A larger one opens a "download in parts" page (200, HTML), which says how many rows and parts it holds. Its script, `src/js/admin-export.js` (the only admin script), fetches each part with `paged=1` (`X-Export-Rows` gives the part's rows, and `X-Export-Next` the next part's cursor while more remain), keeps the parts as Blobs, and saves one file through a temporary `<a download>`. Only the first part carries the byte-order mark and the header. **This page needs JavaScript** (decision B5, the admin-only exception to §11): without it, it says so plainly. The script stops after 1,000 parts, makes no console calls, uses no storage, and announces progress at most every 5 seconds.
  - No response is ever a partial file: a part is built before it is sent, a D1 failure answers 500 `Server error`, and the script saves nothing after any failure (a non-2xx, a network error, a redirect to the Access sign-in, a 30-second timeout).
- **The D1 read budget** (decision B5). D1 Free allows 5 million rows read a day for the whole account, and once they are used up every query fails until 00:00 UTC, visitors' ratings, feedback and events included (§17). An export reads about 2 rows per row sent. So before any download starts (a one-file download, the download page, or a first part), a count capped at 100,001 rows runs (it reads at most that many index entries), and more than 100,000 rows is a 400. With the 31-day limit, one download at the cap reads about 400,000 rows: 8% of a day's allowance. Longer periods are downloaded a month at a time. A later part runs no count, so its cursor's `skip`, the part's SQL `OFFSET`, is at most the row cap (a 400 otherwise): a real cursor's `skip` counts rows already sent, all among the rows the count capped, so only a forged one can be larger, and it can't make a part step over more rows than one download holds.
- **CSV format.** UTF-8 with a byte-order mark (so Excel opens it as UTF-8 by double-click), CRLF line ends and a header row (RFC 4180). Every text cell is quoted, header included, with `"` doubled; numbers are bare; NULL is an empty field. Before quoting, a text cell that starts with `=`, `+`, `-`, `@`, a tab, CR, LF, a full-width `＝`, `＋`, `－` or `＠`, or `'` gets a leading `'`, so a spreadsheet shows it as text, and removing one leading `'` always gives back the stored text (OWASP CSV injection). OWASP warns that "Microsoft Excel may remove quotes or escape characters from CSV cells when a file is saved and re-opened", so a file saved from Excel is no longer guarded. Tests cover a query and a feedback message that start with `=`, and with `＝`. Headers: `Content-Type: text/csv; charset=utf-8; header=present` and `Content-Disposition: attachment; filename="sleepsteps-<table>-<from>-to-<to>.csv"`, built from the checked table and dates only (`worker/lib/csv.js`; `scripts/lib/csv.js` stays the parser, used to read exports back in the tests).
- **Never show `events.id`.** Ids are sequential, so a search row's id falls among the ids of the visit it came from, and would link the search text back to that visit (§10.1). No admin query selects `events.id` or orders by it, and every events read is an aggregate or has a complete `ORDER BY` on content. Measured locally: `ORDER BY ts` alone returns rows with the same `ts` in id order, which is why the tie-break runs through every column. A test exports the same rows inserted in two id orders and gets byte-identical files. Every admin SQL statement is a constant in `worker/lib/admin-queries.js`, run with `prepare().bind()`; a source test forbids SQL anywhere else, `SELECT *`, an events statement that names an id, and `ORDER BY … id` outside the ratings and feedback statements.
- **Headers.** Every admin response, errors and HEAD included, carries `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, `X-Robots-Tag: noindex, nofollow`, `Referrer-Policy: same-origin`, `X-Frame-Options: DENY`, `Cross-Origin-Resource-Policy: same-origin`, the §16.1 `Permissions-Policy`, and an enforced (not Report-Only) CSP: `default-src 'none'; style-src 'self'; img-src 'self'; form-action 'self' https://<ACCESS_TEAM_DOMAIN>; base-uri 'none'; frame-ancestors 'none'`. With no `script-src`, a missed escape can't run script. The download page alone adds `script-src 'self'; connect-src 'self'`. `form-action` names the team (only when the var is well formed) because Chrome checks it on the redirect to the Access sign-in once the session has ended. No admin response sets a cookie. All HTML goes through `html` in `worker/lib/html.js`, which escapes every value and has no way to insert text unescaped; attributes are always double-quoted.
- **Logging.** Four fixed lines, each with a code from a closed list: `/admin: access denied` (the reason: `host`, a verifier code or `error`), `/admin: access certs unavailable` (`status`, `timeout`, `network`, `bad-response` or `no-keys`), `/admin: database read failed` (the `D1_…` code, or `unknown`) and `/admin: unexpected error`. Never the token, a claim, the URL, the query, a header or a row.

## 16. Security, headers and bots

### 16.1 HTTP headers (`_headers` file for static assets; the Worker sets them on its own responses)

- **The `_headers` file** is `src/_headers`, copied to `dist/_headers` by the build. Wrangler reads it as configuration and never serves it, but doesn't parse it on deploy, so a bad line may be dropped without warning. `test/node/deploy-config.test.js` therefore parses it as Cloudflare does (a port of the parser Wrangler bundles) and fails on any line that would be dropped: more than 100 rules, lines over 2,000 characters, URLs that aren't relative or `https`, ports, more than one `*`, malformed headers. Its rules apply to static-asset responses, including the 404 page (seen in local `wrangler dev`; the docs don't say), but not to responses the Worker builds itself. Until M7 adds the headers below, it holds only `X-Robots-Tag: noindex`, for `https://:version.:subdomain.workers.dev/*` (production on `workers.dev` before launch, and always the preview and version URLs there, so it stays after launch; it can't match the custom domain, §18.3) and for `/404` (the 404 page is also served at that path, with a 200). The test also fails on any other rule that would mark pages noindex on every host.
- `Content-Security-Policy`: start from the policy below. Deploy as `Content-Security-Policy-Report-Only` first, fix any violations shown in the browser console, then enforce.
  ```
  default-src 'self';
  script-src 'self' https://www.youtube.com https://challenges.cloudflare.com;
  frame-src https://www.youtube-nocookie.com https://challenges.cloudflare.com;
  img-src 'self' data:;
  connect-src 'self';
  style-src 'self';
  base-uri 'self'; form-action 'self'; frame-ancestors 'none'
  ```
- **Turnstile (M5) needs no change to this policy:** `script-src` and `frame-src` already allow `https://challenges.cloudflare.com`, as Cloudflare's CSP guidance lists, and `connect-src 'self'` is enough, since only pre-clearance (off, §18.4 step 5) would need Cloudflare there. `feedback.js` adds Turnstile's script at run time, so the built HTML never names it and the build-output test can't see it; a source test pins its exact URL instead (§13). M7's Report-Only run checks that Turnstile needs nothing more, for example under `style-src 'self'` (its `api.js` styles the widget through CSSOM, inside a closed shadow root). `src/_headers` doesn't change in M5. `feedback.js` also sets two custom properties on the dialog through the CSSOM while an on-screen keyboard is open (§13); `style-src` governs `style` attributes, `<style>` elements and style sheets, not CSSOM property writes (MDN: "styles properties that are set directly on the element's `style` property will not be blocked"), so this needs no change either: in Chrome 157 under `style-src 'self'` the fit raised no violation, while a test `setAttribute('style', …)` was blocked.
- **Links to other sites** load nothing, so the CSP doesn't cover them. They are kept deliberate instead: a build test allows `<a href>` only to hosts on its allowlist (`www.youtube.com` for "Watch on YouTube", §9.1, and YouTube's Terms of Service on /privacy/, §15.2; `policies.google.com` for Google's privacy policy, §15.2; `creativecommons.org` for the content licence in the footer, §22; `www.cancer.org.au` for Cancer Council on Getting urgent help and Get more help, §7.4), over `https`, with `rel="noreferrer"` so the other site isn't told the visitor came from SleepSteps. Every other attribute that loads something (`src`, `srcset`, `poster`, `<link href>`, `action`, …) must be same-origin.
- `Referrer-Policy: strict-origin-when-cross-origin` (YouTube's recommended value; embedded videos don't play without a `Referer`, §9.1). The search page alone tightens it to `strict-origin` with a meta tag (`referrer` front matter, §8.1), which also keeps the query out of the `Referer` of its search event's request (§10.1). **No page may ever use `no-referrer`**: besides breaking YouTube, it makes the browser send `Origin: null` with the page's beacons, which the API's origin check refuses (§14.1).
- **The Worker's own responses.** `run_worker_first: ["/api/*", "/admin", "/admin/*"]` (§18.2) sends every `/api/*`, `/admin` and `/admin/*` request to the Worker, so `_headers` never applies to API or admin responses. The Worker sets `X-Content-Type-Options: nosniff` and `Cache-Control: no-store` on each API response itself (§14.1); M7 decides which of the other headers here they also need. The admin responses carry their own headers and an enforced CSP from M6, stricter than the site's (`default-src 'none'`, no `script-src` except on the download page, §14.4). The admin pages' `admin.css` and `admin-export.js` are ordinary static assets: they hold no data and get the `_headers` rules.
- `X-Content-Type-Options: nosniff`
- `Permissions-Policy: camera=(), microphone=(), geolocation=()`

Only the YouTube IFrame API (loaded on click) and Turnstile, loaded the first time the feedback dialog opens on a page (§13): from the exact URL Cloudflare gives, `https://challenges.cloudflare.com/turnstile/v0/api.js?render=explicit`, with no preconnect, no SRI and no self-hosted copy (Cloudflare: "The api.js file must be fetched from the exact URL shown above"), and never while production's site key is still the placeholder. ### 16.3 Cloudflare dashboard settings (manual, see §18)

These apply to the custom domain only, never to `workers.dev` or preview URLs.

- DNS records proxied; Always Use HTTPS
- AI Crawler and Agent access policies: Search **Allow**; Training **Disallow** (not Block, which also catches crawlers used for both search and training) with "Bot Preference Sync" on, which writes the managed robots.txt; Agent and Personal Agents at team discretion (§21)
- Bot Fight Mode: **Off** at launch, held in reserve. It barely protects the real risk (`/api/*` using up the D1 budget), can silently drop real beacons it challenges, and on the Free plan can't be skipped for `/api/*`. Its injected script needs a per-response CSP nonce, which would put the Worker in front of every page. **Triggers** for revisiting: bot traffic visible in `/admin`, D1 nearing its daily limit, or feedback spam getting past Turnstile. **Fallbacks, in order:** the Workers Rate Limiting binding on `/api/event`, if it works on Free (looked at in M3 and not added: Wrangler's configuration schema accepts it, previews included, but Cloudflare doesn't say whether Workers Free includes it, and a workers-sdk issue, #16097, reports it never enforcing there); Bot Fight Mode with `Cache-Control: no-transform` on HTML (no injected script; HTML loses compression); Bot Fight Mode with a Worker-set nonce, only on Workers Paid. Before turning it on, add `__cf_bm` to the privacy page (§15.4; the privacy officer should pre-approve the wording).
- Web Analytics (RUM): **Off.** It is on by default for Free zones and injects a third-party analytics script (§16.2). Once off, Cloudflare says it won't re-enable it.
- Email Address Obfuscation (Scrape Shield): **Off.** It is on by default, injects a script and rewrites email addresses, breaking the CSP and the no-JavaScript rule.
- Challenge Passage: **30 minutes**, matching the privacy page's `cf_clearance` row.
- At launch, check the live HTML in a real browser for `cloudflareinsights`, `email-decode` and `challenge-platform` (none should appear), and check stored items in browser devtools against §15.4.
- Rate-limiting rule: URI path starts with `/api/`, 20 requests per 10 seconds per IP → block for 10 seconds. The Free plan allows one rule, can't match on method, and returns Cloudflare's default 429. It limits bursts from each IP, not the total, so it doesn't protect the daily D1 budget. It covers only the custom domain: if production's API is ever opened on `workers.dev` (§14.1, §21), nothing rate-limits it there, so revisit the binding first.
- Search engines allowed. Verify crawling in Google Search Console after launch.

## 17. Database

Production uses `sleepsteps` (`7da77651-1695-4331-8708-114382f04757`) and Worker Previews use `sleepsteps-preview` (`38b5ff0a-4518-4aa0-b884-c93546b9ee56`) (§18.2), both created on 2026-11-06 with `wrangler d1 create <name> --location=oc`. A test pins both IDs, so they can't be swapped. The location hint affects placement only and is not a data-residency guarantee. All previews share `sleepsteps-preview`, which holds test data only: it is never exported for analysis (downloading its seeded test rows to check the file format is allowed, §18.4 step 6c), and is emptied when no longer needed. Its writes count against the same account limits as production's (below).

`migrations/0001_init.sql` (applied to the local database on 2026-11-06, not yet to either remote one) holds exactly this schema, under a header saying it must never be edited once applied remotely. It uses no `AUTOINCREMENT`. Search events are rows in `events` with `session_id` NULL (§10.1); there is no separate table for them (§22).

```sql
CREATE TABLE ratings (
  id INTEGER PRIMARY KEY,
  ts TEXT NOT NULL,
  page TEXT NOT NULL,
  video TEXT NOT NULL,
  stars INTEGER NOT NULL CHECK (stars BETWEEN 1 AND 5)
);
CREATE TABLE feedback (
  id INTEGER PRIMARY KEY,
  ts TEXT NOT NULL,
  page TEXT NOT NULL,
  page_title TEXT,
  message TEXT NOT NULL
);
CREATE TABLE events (
  id INTEGER PRIMARY KEY,
  ts TEXT NOT NULL,
  session_id TEXT,
  page TEXT NOT NULL,
  type TEXT NOT NULL,
  detail TEXT
);
CREATE INDEX idx_ratings_ts ON ratings(ts);
CREATE INDEX idx_feedback_ts ON feedback(ts);
CREATE INDEX idx_events_type_ts ON events(type, ts);
```

One secondary index per table: every insert writes 2 rows (the row plus one index entry). The admin summary filters events by `type = ?` or `type IN (...)` and a `ts` window, so it uses `idx_events_type_ts`, and ratings and feedback by a `ts` window (§14.4). Export parts make one query per event type (`type = ?`), which walks the index in order and stops early: about 2 rows read per row sent. (Measured locally: `type IN (all five)` with `ORDER BY ts … LIMIT n` sorts the whole range for every part, and with no type filter SQLite scans the table.) A test checks every admin query's plan. M6 needed no new index or migration.

Schema changes go through new migration files only: `wrangler d1 migrations create`, or a file written by hand in its format (`NNNN_name.sql`, which a test checks), then `npm run db:migrate:local` before any remote apply. Never edit an applied migration: D1 records only a migration's file name, so an edited file never reaches a database that already applied it. `test/node/deploy-config.test.js` pins each migration's SHA-256 (from `0001_init.sql`), so an in-place edit fails the tests; a schema change is a new `NNNN_name.sql`, whose hash is added once it is applied anywhere remote.

**Remote migrations are human-only (§18.4), and needed only where something uses the database.** While `DATA_COLLECTION` is off in an environment, its API answers 404 before touching D1 (§14.1). So:
- An environment needs its migrations only before collection is turned on there, and, from M6, before the admin page is used there (until then the page says "The database isn't set up here yet"). Production gets `npm run db:migrate:remote` before the go-ahead PR merges (§18.3). Previews get `npm run db:migrate:preview` before their admin page is used (§18.4 step 6b) or their collection is turned on (§21), whichever comes first.
- Once collection is on in an environment, apply each new migration there before the code that needs it deploys: `npm run db:migrate:preview` when its pull request opens, and `npm run db:migrate:remote` just before it merges to `main`.
- Nothing else in M3–M6 waits for a remote migration.

**In the tests**, each Worker test file starts from an empty D1 of its own. `vitest.config.js` reads `migrations/` with `readD1Migrations` and passes the files in as the `TEST_MIGRATIONS` binding, and `test/worker/apply-migrations.js` (a setup file) applies them with `applyD1Migrations` before the file's tests run. Rows persist between the tests in one file, so a file clears its rows with `DELETE`; never `reset()`, which also drops the schema. `test/worker/schema.test.js` checks that the migrations create exactly the tables, columns and indexes above.

Workers Builds doesn't apply migrations (its API token has no D1 permission). `wrangler d1` commands read only the top-level `d1_databases`, so the preview database is reached through `wrangler.preview-migrations.jsonc`, which declares just that database. D1's `--preview` flag belongs to an older feature (`preview_database_id`) and is not used.

Free plan limits (Nov 2026): 100,000 rows written/day and 5 million rows read/day **per account**, and a 500 MB database. Each secondary index adds a written row, so one insert costs 2 rows (§17 schema): the real ceiling is about 50,000 events a day. Once either daily limit is hit, **every** D1 query fails until 00:00 UTC (10:00 AEST, 11:00 AEDT): saving, the admin page and the export. Pages and media keep working, and there is never a bill. The 500 MB cap does not reset. The free plan's point-in-time recovery covers only 7 days, so monthly CSV exports are the real backup. D1 Free also allows 50 queries per Worker invocation (a batch counts as one), 2 MB per row and 50 MB per query result (from 2026-11-04).

**The admin pages' reads** (measured locally; whether production counts rows read the same way is checked at §18.4 step 6c, against the number the page shows). A summary load reads about 2.6 times the events in its range, and an export about 2 rows per row sent, plus a capped count of at most 100,001 index entries before it starts. Because a staff member's reads share the account's 5 million a day with every visitor, each request is capped (§14.4):
- **The summary** accepts at most 92 days (decision B3). The cost follows traffic, not days: at 2,000 events a day a 92-day load reads about 0.5 million rows (10% of a day's allowance), at 5,000 a day about 1.2 million (24%), and at 20,000 a day about 4.8 million, nearly all of it. So the footer shows the rows each load read, and over 500,000 (10%) asks staff to choose shorter ranges and tell the developer. **Trigger:** if loads often pass that, lower `MAX_SUMMARY_DAYS` (`worker/lib/date-range.js`).
- **A download** covers at most 31 days and 100,000 rows (decision B5): at the cap, about 400,000 rows read (8%). Above about 3,200 usage events a day, a month's events file passes 100,000 rows and its "Last month" link answers with the too-many-rows message; staff then choose shorter ranges on the summary page (half a month, say), whose download links cover exactly that range. If that becomes the rule rather than the exception, revisit the caps, or Workers Paid (below).

If limits become a problem, upgrade to Workers Paid (US$5/month): no daily cut-off, 10 GB per database and 30-day point-in-time recovery. The plan switch itself needs no code changes. Export paging, index-friendly admin queries and any retention job are needed on either plan (§14.4). Use a Cloudflare account dedicated to this project, since the limits are shared across the account.

### 18.2 `wrangler.jsonc` (skeleton)

```jsonc
{
  "name": "sleepsteps",
  "main": "worker/index.js",
  "compatibility_date": "<DATE OF SETUP>",
  "assets": {
    "directory": "./dist", "binding": "ASSETS", "not_found_handling": "404-page",
    "run_worker_first": ["/api/*", "/admin", "/admin/*"]   // both admin entries: "/admin/*" doesn't match "/admin"
  },
  "observability": { "enabled": false },   // Workers Logs off (§14.1)
  "workers_dev": true,      // false from launch
  "preview_urls": true,
  "d1_databases": [
    { "binding": "DB", "database_name": "sleepsteps", "database_id": "<ID>", "migrations_dir": "migrations" }
  ],
  "vars": { "ACCESS_TEAM_DOMAIN": "<TEAM>.cloudflareaccess.com",   // no scheme
            "ACCESS_AUD": "<AUD_TAG>",   // the /admin application's AUD (§14.4)
            "DATA_COLLECTION": "off", "API_HOSTS": "<DOMAIN>" },
  // Secrets (set with `wrangler secret put`, never committed): TURNSTILE_SECRET.
  // No "secrets": { "required": [...] } list (§14.3)
  "previews": {
    "observability": { "enabled": false },   // not inherited
    "d1_databases": [ { "binding": "DB", "database_name": "sleepsteps-preview", "database_id": "<PREVIEW ID>" } ],
    "vars": { "ACCESS_TEAM_DOMAIN": "<TEAM>.cloudflareaccess.com",
              "ACCESS_AUD": "<AUD_TAG>",   // the Worker-level ("Previews only") application's AUD
              "DATA_COLLECTION": "off", "API_HOSTS": "*-sleepsteps.*.workers.dev" }
  }
}
```

- `compatibility_date` must be no later than the newest date the pinned Wrangler's bundled workerd supports; otherwise `wrangler dev` refuses to start. Raise it when upgrading Wrangler.
- **Routing.** With this compatibility date, a browser *navigation* to a path with no matching file gets the 404 page straight from static assets, without the Worker running. Other unmatched requests (fetch, beacons, crawlers' `robots.txt`) reach the Worker, and the `ASSETS` binding lets it hand non-`/api/`, non-`/admin/` ones back to static assets. `run_worker_first` sends `/api/*` to the Worker first (from M3), so the API answers even where a file matches, and `/admin` and `/admin/*` (from M6), which `/admin/` page loads need. Both admin entries are needed: the asset router compiles `/admin/*` to `^/admin/.*$`, which doesn't match `/admin`.
- **Workers Logs** (`observability`) is off at the top level and in `previews`, which doesn't inherit it: invocation logs record request metadata, which the API must not store (§14.1). `wrangler tail` still shows live logs.
- **`API_HOSTS`** lists the hosts the API and the admin pages answer on (§14.1, §14.4): `"<DOMAIN>"` in production, which matches no host until the launch PR sets the domain, and `"*-sleepsteps.*.workers.dev"` in previews. Every host listed must be behind an Access application that covers `/admin` and `/admin/*` (§14.1).
- **`ACCESS_TEAM_DOMAIN` and `ACCESS_AUD`** (§14.4) stay the placeholders until a person sets up Access (§18.4 step 6); until then every admin request answers 403 everywhere and nothing is fetched. The team domain is the same in both blocks and has no scheme. Production's AUD is the `/admin` self-hosted application's; previews' is the Worker-level application's ("Previews only"), since on preview hosts the Worker-level application is the one that applies, so the two AUDs differ.
- **Previews.** Worker Previews (every branch but `main`, §18.3) inherit no vars or bindings from the top level, so the `previews` block repeats them: its own `DB` binding to `sleepsteps-preview` and every var (`DATA_COLLECTION` is off there too until previews are behind Access, §11). `assets`, `main` and `compatibility_date` come from the top level. `wrangler preview` refuses to run without a `previews` block. Preview secrets are set with `wrangler preview base-config secret put` and reach only previews created afterwards. Preview migrations use `wrangler.preview-migrations.jsonc` (§17).
- **Tests** (`test/node/deploy-config.test.js`) check that:
  - the previews block has every production var and its own database;
  - `DATA_COLLECTION` is `"off"` in both blocks;
  - `run_worker_first` is exactly `/api/*`, `/admin` and `/admin/*`;
  - `ACCESS_TEAM_DOMAIN` and `ACCESS_AUD` in each block are the placeholder or well formed (`<name>.cloudflareaccess.com`; 64 hex characters), with one team once both are real, and previews' AUD different from production's;
  - there is no `access` key (`access.dev` only simulates `ctx.access`, which this Worker never gets, §14.4);
  - `observability.enabled` is false in both blocks;
  - production's `API_HOSTS` has no `*`, and each entry is `<DOMAIN>`, `siteUrl`'s host or `sleepsteps.<subdomain>.workers.dev`. Once `siteUrl` is real, its host must be in the list, and no entry may ever match a version URL;
  - previews' `API_HOSTS` is exactly the wildcard pattern, which accepts a preview URL but not production's `workers.dev` host;
  - `migrations/` holds only numbered SQL files, starting with `0001_init.sql`;
  - `dev:collect` sets both vars with `--var`, and no `.dev.vars` or `.env` file (`.env`, `.env.local`, …) may set either: `wrangler dev` and the Worker tests read those files too, so a copied line would turn collection on for every local run. A test checks them, and `.env*` is git-ignored;
  - `TURNSTILE_SECRET` (§14.3) is in neither vars block, and neither block has a `secrets` key: `secrets.required` would fail every build and deploy until a person had set the secret. `dev:collect` passes exactly Cloudflare's always-pass test secret (`--var TURNSTILE_SECRET:1x0000000000000000000000000000000AA`), and no other script mentions it. A `.dev.vars` or `.env` file may set `TURNSTILE_SECRET`, but only to one of Cloudflare's three published test secrets (`1x…AA` passes, `2x…AA` fails, `3x…AA` answers as a spent token).
- **Locally**, `wrangler dev` and the tests use only the top level, never the `previews` block, so they act like production: `wrangler dev` uses a local copy of the `sleepsteps` database, and the tests an empty one of their own. No binding may be marked `"remote": true`, which would point them at the real database.
- **No `account_id`.** Workers Builds supplies the account, and a mismatched `account_id` fails the build. Run Wrangler's remote commands logged in to the SleepSteps account.
- **At launch**, `"workers_dev": false` stops production answering on `workers.dev` (switching it off in the dashboard is undone by the next deploy), and `preview_urls` stays on. It is already set explicitly, because when it is missing a new Worker copies `workers_dev`. It also turns on version URLs (`<version>-sleepsteps.<subdomain>.workers.dev`), one for every production deploy, which stay public after launch and run that version's code on production's database, outside the custom domain's rate limit (§16.3). The `_headers` noindex rule covers them (§16.1), and the API must not accept writes through them: production's API answers only on the hosts in production's `API_HOSTS` (none until launch, then the domain), and a version URL never matches (§14.1). For the same reason the admin pages answer 403 there (§14.4). Wrangler has a single setting for preview and version URLs, so they can't be turned off separately.

### 18.3 Deployment

Workers Builds is connected to the GitHub repo. Pushes to `main` build and deploy to production (`npx wrangler deploy`). Other branches build **Worker Previews** with `npx wrangler preview`, the default Preview command for a new Worker, each at `<branch>-sleepsteps.<subdomain>.workers.dev`. **Previews use the separate `sleepsteps-preview` database** and their own vars from the `previews` block (§18.2). (`npx wrangler versions upload`, the older preview model, would run branches on production's database; don't use it.)

- **The Worker must be named exactly `sleepsteps`**, the `name` in `wrangler.jsonc`. Otherwise the build fails (Cloudflare's docs), or with Wrangler 4.153.0 deploys under the dashboard's name while Builds tries to open a pull request renaming the config.
- **Build command:** `npm test && npm run build`, so a failing test stops the deploy. It runs for preview builds too (Free plan: 3,000 build minutes a month, one build at a time, 20-minute timeout). Deploy command `npx wrangler deploy`; Preview command `npx wrangler preview`.
- **Pinned versions.** Builds ignores `engines`, so Node is pinned exactly in `.node-version` (24.22.1, the Builds image's default and preinstalled version in November 2026) and npm in package.json's `packageManager` (`npm@11.18.0`; Builds otherwise uses npm 10.9.2, which ignores `allowScripts`). Local development may use a newer Node within `engines`. Raise the pins deliberately, after `npm ci && npm test && npm run build` passes on the new versions.
- **The setup PR merges first.** The real D1 IDs and the `previews` block must be on `main` before Builds is connected, or the first deploy fails.
- **Before launch the site is unlisted.** Production is public at `sleepsteps.<subdomain>.workers.dev` as soon as Builds deploys, and zone settings (§16.3) don't apply there. Until launch:
  - every `workers.dev` address sends `X-Robots-Tag: noindex`, from `_headers` (§16.1). Cloudflare's docs describe the automatic header only for preview URLs, so production on `workers.dev` relies on this rule; §18.4 step 7 checks it after the first deploy;
  - data collection stays off in production until the privacy officer's go-ahead, and in previews until they are behind Access: `DATA_COLLECTION` is `"off"` in both (§11). Turning it on is a reviewed one-line change to `wrangler.jsonc`, after the environment's remote migrations are applied (§17). Pages still load `events.js` meanwhile, and the API answers 404 (§11);
  - production's `API_HOSTS` is `"<DOMAIN>"`, so its API and admin pages answer on no host. If the go-ahead comes before launch, the go-ahead PR decides whether to add `sleepsteps.<subdomain>.workers.dev`, which has no rate-limiting rule (§16.3, §21) and would need the `/admin` Access application to cover that host first (§14.1, §18.4 step 6e).
- **At launch** the custom domain is added, and one PR sets `siteUrl` and `API_HOSTS` to the domain, production's `ACCESS_AUD` to the `/admin` application's AUD (§18.4 step 6d) and `workers_dev` to false (§18.2).
